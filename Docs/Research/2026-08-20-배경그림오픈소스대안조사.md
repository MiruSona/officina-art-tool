# 배경 그림 : PixelLab 없이 가는 길 조사

> 앞선 조사 : `Docs/Research/2026-08-20-배경그림조사.md`
> 거기서 PixelLab 을 추천했으나 **키트에 유료 서비스가 필수가 되는 문제**가 있어 대안을 다시 찾았다.

## 결론 먼저

1. **PixelLab 은 필수가 아니어도 된다.** PixelLab 이 해주던 일의 **대부분이 그림 그리기가 아니라 부풀리기**인데, 그 부풀리기는 **오픈소스에 이미 다 있고 순수 코드로 돌아간다.**
2. **팔레트 교체가 제일 싸고 강력하다.** 타일셋 하나로 숲 / 유령숲 / 가을숲을 만든다. 코드만으로 되고, 덤으로 **"캐릭터와 배경 그림체가 안 맞는" 문제까지 같이 풀린다.** (출처가 다른 에셋도 팔레트를 맞추면 한 사람이 그린 것처럼 보인다)
3. **제공자를 갈아끼우는 구조로 간다.** 툴 인터페이스는 하나, 뒤에 붙는 그림 생성기는 교체 가능하게. **기본은 무료 경로, PixelLab 은 키를 넣으면 켜지는 선택지.** 캐릭터 툴도 같은 구조로 가면 일관된다.

---

## 1. 핵심 : ①이 다시 둘로 쪼개진다

앞 조사에서 배경을 ① 타일 그림 / ② 이어붙이기 / ③ 배치 로 나눴다. 그런데 **①이 또 둘로 나뉜다.**

| | 하는 일 | AI 필요? |
| --- | --- | --- |
| **①-a 재료 그림** | 풀·흙·돌 텍스처 한 장 | 있으면 좋지만 **없어도 됨** (기반 에셋 + 변형) |
| **①-b 부풀리기** | 그 한 장을 15장 / 47장 오토타일 세트로 | **전혀 필요 없음. 100% 코드** |

PixelLab 이 대단해 보였던 이유는 ①-a 와 ①-b 를 한 번에 해줘서다. **그런데 ①-b 는 오픈소스 도구들이 이미 하고 있다.** 그러면 남는 건 ①-a 뿐이고, 그건 "기반 이미지 제공 → 변형" 방식으로 충분히 메울 수 있다.

---

## 2. 무료 경로 (기본값으로 삼을 것)

### 2-1. 팔레트 교체 — 제일 먼저 할 것

같은 타일셋을 색만 바꿔 다른 지역으로 쓴다. 숲 타일셋 → 보라·회색이면 유령숲, 주황·갈색이면 가을숲.

- **색 램프 단위로 묶는다.** 풀 램프 3~4단, 흙 램프 3~4단 식으로. 밝고 어두운 관계를 그대로 유지한 채 색만 옮긴다.
- **정적 방식** : 미리 여러 벌을 구워둔다. 간단함.
- **런타임 셰이더 방식** : 스프라이트를 키 컬러(순수 빨강·초록 등)로 그려두고 셰이더가 팔레트 텍스처를 보고 바꾼다. **텍스처 메모리를 안 늘리고 변형 수가 무한**이다.
- 팔레트는 Lospec 등에서 가져온다.

> **덤** : 앞 조사에서 미해결로 남겼던 "캐릭터와 배경 그림체 맞추기"가 여기서 풀린다.
> 팔레트를 프로필에 고정해두면 출처가 다른 에셋들이 같은 그림처럼 보인다.

### 2-2. 오토타일 부풀리기 (①-b) — 오픈소스가 있다

| 이름 | 뭘 하나 | 메모 |
| --- | --- | --- |
| **TilePipe / TilePipe2** | 타일 조각 → **47장 blob**, 16장, 최대 256장까지. **규칙(ruleset)을 직접 만들 수 있음** | 2022-03 부터 오픈소스. 콜리전 도형 자동 생성까지 있음. **제일 유력** |
| `itsjavi/autotiler` | 47장 blob 생성기 | Electron 기반 |
| `route1rodent/autotiler` | **15장 → 42장 blob** 변환 | 오픈소스 |
| `FabriceLing/autotile` | Godot용 | 참고용 |
| Unity **RuleTile** | 엔진 기본 제공 | 규칙만 있으면 부풀리기 없이 바로 씀 |

**"규칙을 직접 만들 수 있다"** 는 게 우리한테 중요하다. 우리 프로필(투영 3종)마다 규칙을 다르게 둘 수 있다.

### 2-3. 텍스처 합성 (①-a) — 한 장에서 여러 장

기반 이미지를 넣으면 **비슷하지만 다른** 이미지를 뱉는 방식이다. 캐릭터 때 이야기했던 "변형" 이 배경에서는 이 이름으로 불린다.

| 이름 | 방식 | 메모 |
| --- | --- | --- |
| **EmbarkStudios/texture-synthesis** | Rust, 예시 기반 합성. **inpaint + tiling 을 같이 쓰면 기존 이미지를 이어지게 만들 수 있다** | 라이브러리 + CLI 둘 다 있음. 명령줄로 부르기 좋음 |
| `sashaouellet/WangTile` | 이미지 퀼팅(image quilting) + Wang 타일 | 반복이 거의 안 보이는 큰 텍스처를 만듦 |
| `lzqsd/TileableTextureSynthesis` | 그래프 컷 기반 | **텍스처의 구조를 유지**하는 게 강점 |

> **주의** : 이 도구들은 원래 **사진 텍스처용**이다. 64×64 픽셀아트에 그대로 돌리면 픽셀이 뭉개지거나 색이 늘어날 수 있다.
> 합성 후 **팔레트로 다시 눌러주는(양자화) 단계**가 반드시 필요해 보인다. 실제로 해봐야 안다.

### 2-4. 기반 에셋

- **Kenney** (CC0), **OpenGameArt** 의 타일셋·배경 묶음
- 우리 방침이 원래 "백지에서 안 그리고 기존 그림을 변형" 이라 잘 맞는다
- **투영별로 따로 갖춰야 한다** (앞서 정한 대로 투영이 다르면 재사용 불가)

## 3. 선택 경로 (있으면 좋은 것)

### 3-1. 로컬 이미지 모델 — 미니PC 에서

- `nerijs/pixel-art-xl` (SDXL LoRA) — 픽셀아트 LoRA 중 가장 많이 쓰임. 트리거 단어 없이 프롬프트에 "pixel" 만 넣으면 됨
- LCM LoRA 를 같이 쓰면 25~30 스텝을 **8 스텝**으로 줄임
- `Limbicnation` 의 FLUX.2-klein-4B 픽셀아트 LoRA (2026) — 더 최신
- **img2img 로 낮은 강도** 를 주면 "기반 이미지 → 변형" 이 그대로 된다
- 단점 : 무겁고 결과가 들쭉날쭉하다. **생성 후 팔레트 양자화와 크기 정리는 어차피 코드로 해야 한다**

### 3-2. PixelLab — 플러그인으로

- 품질·속도는 여전히 제일 낫고 MCP 도 있다
- **키트에 필수로 넣지 말고, 키를 넣으면 켜지는 제공자로 둔다**
- Pro 이상 결제하셨으니 우리 프로젝트에서는 실제로 쓰면 된다. **다만 키트를 받는 남이 없어도 돌아가야 한다**

## 4. 그래서 어떤 구조로

```
        배경 툴 (인터페이스 하나)
                 │
      ┌──────────┼──────────┐
   기본 제공자   로컬 모델   PixelLab
   (무료·코드)   (선택)      (선택·유료)
      │
   에셋 + 팔레트 교체 + 텍스처 합성
                 │
      ┌──────────┴──────────┐
   오토타일 부풀리기      배치 (WFC / 룰)
   (TilePipe 계열)              │
                          LDtk 내보내기
```

- **제공자만 갈아끼운다.** 툴을 부르는 쪽 코드는 안 바뀐다.
- **기본 제공자는 순수 코드**라 인터넷도 결제도 필요 없다. 키트로서 성립한다.
- **캐릭터 툴도 같은 구조**로 가면 규칙이 하나가 된다.

---

## 5. 아직 확인 못 한 것

- **텍스처 합성 도구들이 64×64 픽셀아트에서 쓸 만한지** — 이게 제일 큰 미지수다. 실제로 돌려봐야 한다
- TilePipe / autotiler 계열의 **정확한 라이선스**와 최근 커밋 상태 (검색 결과만 봄, 저장소 직접 확인 안 함)
- **47장 blob 은 사각 타일 전용**이다. 아이소메트릭은 규칙을 따로 만들어야 하는데 얼마나 드는지 모름
- TilePipe 는 Godot 내보내기가 중심이다. **Unity 로 가져오는 경로**를 우리가 만들어야 할 수도 있음
- 로컬 모델을 미니PC 에서 돌릴 때 Qwen(코딩용)과 **VRAM 을 나눠 쓸 수 있는지**
