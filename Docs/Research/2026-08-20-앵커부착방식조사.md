# 앵커 기반 부착 방식 조사 (탑다운)

대상: 시점이 **탑다운**으로 확정된 뒤, 코스튬 약 40종을 어떤 방식으로 만들지.
사람 캐릭터 + 비인간 캐릭터(슬라임) 둘 다 다룬다. 무기는 없다. 캔버스 64×64.
앞 조사(`2026-08-19-2D그림툴조사.md`, `2026-08-20-사이드뷰2D소스조사.md`)의 후속이다. 앞 문서는 그대로 둔다.

## 결론 먼저

1. **한 툴에서 두 방식을 다 쓴다. 캐릭터 종류로 갈린다.** 사람은 **LPC 층 겹치기**, 슬라임은 **앵커 부착**이다. 시점이 아니라 **rig(몸 구조)** 가 방식을 정한다. 프로필 파일에 `rig: humanoid_lpc | blob` 로 적고 툴이 갈라 쓴다.
2. **LPC 규격에는 앵커가 없다. 순수 층 겹치기다.** 정의 파일 657개를 전부 열어 확인했다 — 부착점·오프셋 필드가 **하나도 없다**(있는 건 UI 미리보기용 `preview_x_offset` 뿐). 모자·날개·꼬리·무기까지 전부 "프레임 전체를 그린 층 + `zPos`" 로 처리한다.
3. **그래서 사람 코스튬은 우리가 그리지 않는다. LPC 기성품을 쓴다.** 옷 한 벌을 층으로 그리려면 **154장**이 필요하다(아래 4장 계산). M=5만 잡아도 770장이라 손으로는 불가능하다. 대신 LPC 에 상의 102종·하의 22종·신발 17종·모자 155종이 이미 있고, **OGA-BY 를 허용하면 657종 중 525종(80%)** 을 쓸 수 있다.
4. **팔레트 스왑의 K 값도 이미 정해져 있다.** LPC 는 재질별 색 램프를 데이터로 갖고 있다 — 옷 **24색**, 전체 팔레트 **75색**, 각각 6단계 램프다. 즉 `M(실루엣) × K(색)` 에서 **K 는 공짜로 24 이상**이다.
5. **40종 구성은 `M 8종 × K 5색 = 40` 이 가장 싸다. 손그림 0장이다.** 슬라임만 다르다 — LPC 밖이라 실루엣을 우리가 만들어야 하는데, 대신 팔다리가 없어 **강체 앵커가 아주 잘 통한다.** 예시 이미지 3장을 픽셀 단위로 재보니 몸 bbox 가 3방향 모두 완전히 같고(`x11..52, y16..50`) 왕관만 방향별로 위치가 다르다. **슬라임 코스튬 = 부착물 1장 + 방향별 앵커 4개.**

## 1. ★ LPC 와 앵커를 한 툴에서 어떻게 섞는가 (설계의 갈림길)

### 1-1. LPC 에는 앵커가 없다 — 실측

저장소를 받아 `sheet_definitions/` 의 JSON **657개**(meta 제외)를 전부 파싱했다.

**등장하는 최상위 키 전부:**

| 키 | 개수 | 뜻 |
| --- | --- | --- |
| `name`, `type_name`, `credits` | 657 | 이름 · 분류 · 저작권 |
| `layer_1` | 657 | 층 1개는 무조건 있다 |
| `animations` | 582 | 이 조각이 지원하는 애니메이션 목록 |
| `recolors` | 434 | 재질 + 적용 가능한 팔레트 |
| `variants` | 223 | 색·종류 변형 목록 |
| `layer_2` ~ `layer_8` | 168 / 30 / 24 / 3 / 3 / 2 | 층이 여러 개인 조각 |
| `tags`, `required_tags`, `priority`, `match_body_color`, `aliases` | 120~22 | 조합 규칙 |
| `preview_x_offset`, `preview_y_offset` | 13 | **UI 썸네일 위치일 뿐, 게임용 앵커가 아니다** |

**`anchor` · `attach` · `pivot` · `origin` 계열 키는 하나도 없다.** 층 순서를 정하는 `zPos` 만 있다.

층 개수 분포: 1층 489개, 2층 138개, 3층 6개, 4층 21개, 6층 1개, 8층 2개.

**결정적인 것**: LPC 는 모자(`headwear` 155종)·날개(`wings`)·꼬리(`tails`)·의족·휠체어까지 전부 **프레임 전체를 그린 층**으로 만든다. "머리에 붙이는 좌표" 같은 개념 자체가 없다. 10년 넘게 수십 명이 만든 가장 성숙한 탑다운 모듈 규격이 앵커를 안 쓴다는 뜻이다.

### 1-2. 왜 그런가

층 방식은 **그림을 많이 그리는 대신 코드가 단순**하다. 프레임 번호만 맞으면 겹치기만 하면 된다. 앵커 방식은 **그림은 1장으로 끝나지만 프레임마다 좌표·앞뒤순서 데이터**가 필요하다.

| | 층 겹치기 (LPC) | 앵커 부착 |
| --- | --- | --- |
| 조각 1개당 그림 | 프레임 수만큼 (154장) | **1장** |
| 필요한 데이터 | 층 순서 1개 | 프레임 × 방향마다 `{x, y, z}` |
| 몸이 휘어도 | 알아서 맞는다 | **안 맞는다** |
| 이미 만들어진 자산 | **LPC 657종** | 없다 |

### 1-3. 그래서 우리 답 — 둘 다 쓰되 rig 로 가른다

```
프로필 파일 (툴 설정)
  view: top-down
  frame: 64x64
  directions: [north, west, south, east]     # east = west 좌우반전
  baseline_y: 50

  rigs:
    humanoid_lpc:                 # 사람 캐릭터
      method: layer               # ← LPC 층 겹치기
      layer_order: [body, legs, feet, torso, arms, hair, headwear]
      source: LPC sheet_definitions
      anchors: []                 # 거의 안 쓴다

    blob:                         # 슬라임 캐릭터
      method: anchor              # ← 앵커 부착
      parts: [body]               # 몸은 통짜 1개
      anchors: [head_top, back, front, ground]
```

- **툴은 하나.** 합성 엔진이 `method` 를 보고 층을 쌓거나 앵커로 붙인다.
- 두 방식이 **한 캐릭터 안에서 섞이는 것도 허용**해야 한다. 사람 캐릭터에도 "손에 든 소품" 같은 건 앵커가 낫다(지금은 무기가 없어 급하지 않다).
- 앵커 데이터 형식은 rig 와 무관하게 하나로 통일한다 → `{ rig, anim, direction, frame, point, x, y, z }`

## 2. 앵커가 통하는 범위 — 탑다운에서 다시 판정

앞 조사(사이드뷰 기준)의 결론 "앵커는 강체에만 통한다"는 **탑다운에서도 대체로 유효하지만, 경계가 조금 넓어진다.**

### 2-1. Stardew Valley 재검토 — 탑다운 실사례

앞 조사에서 "반례처럼 보이지만 조건이 다르다"고 넘겼던 사례다. 탑다운이 되면서 중요해졌으므로 다시 팠다.

확인된 것 (위키 본문은 403 으로 자동 조회가 막혀 검색 요약으로만 확인 — **2차 확인 필요**):

- 캐릭터 스프라이트는 **16×32**
- 베이스 시트가 세 구역으로 나뉜다 — **머리/몸통/신발은 왼쪽 6열, 바지는 오른쪽 6열, 팔은 가운데 12열**
- **모자 · 액세서리 · 바지는 16px 전체 폭 프레임**을 쓴다 = 사실상 **층 방식**
- **셔츠만 8×8 한 장**이고 코드가 프레임마다 위치를 옮긴다 = **앵커 방식**
- 셔츠 위치는 **애니메이션마다 코드에 박혀 있어** PNG 만 고쳐서는 못 바꾼다
- 위키에 "셔츠가 8×8 이라 16px 넓은 몸통을 다 못 덮는다"는 제약이 적혀 있다

→ **탑다운 대표작조차 대부분을 층으로 처리하고, 앵커는 가장 작고 평평한 조각(셔츠) 하나에만 쓴다.** 그리고 그 하나도 "몸통을 다 못 덮는다"는 대가를 치른다.

### 2-2. 탑다운 판정표

| 등급 | 대상 | 앵커 1장으로? | 왜 |
| --- | --- | --- | --- |
| **A** | 모자 · 왕관 · 뿔 · 귀 · 가면 | **된다** | 머리는 방향별로 위치만 바뀐다. 방향당 앵커 1개 |
| **A** | 날개 · 등짐 · 꼬리 뿌리 · 후광 | **된다** | 몸에 붙는 강체 |
| **A** | 발밑 그림자 · 이펙트 | **된다** | ground 앵커 |
| **B** | 가슴팍 문양 · 벨트 · 목걸이 · 작은 앞치마 | **조건부** | 탑다운은 몸통이 정면이라 사이드뷰보다 유리하다. Stardew 셔츠가 이 등급. **덮는 면적이 작을 때만** |
| **C** | 상의 전체 · 소매 | **안 된다** | 걷기에서 팔이 앞뒤로 움직인다. LPC 가 `arms` 를 별도 층으로 둔 이유 |
| **C** | 하의 · 신발 | **안 된다** | 다리가 프레임마다 바뀐다 |

**사이드뷰 대비 달라진 점**: B 등급이 넓어졌다. 탑다운은 팔다리 회전이 화면상에서 덜 보이고, 몸통이 정면이라 가슴팍 장식 정도는 앵커로 붙일 만하다. 하지만 **상의·하의 전체는 여전히 안 된다.**

**앞 조사에서 근거로 쓴 Godot cutout 문서와 Terraria 사례는 사이드뷰 기준이었다.** 탑다운에서의 직접 근거는 위 Stardew 사례와 LPC 규격 자체(층만 쓴다)로 대체한다.

## 3. ★ 앵커 데이터를 누가 만드는가 (최우선 항목)

### 3-1. 규모 — 탑다운은 사이드뷰의 4배

방향이 4개라 앵커도 방향마다 따로 필요하다.

| | 사이드뷰(옛 계산) | **탑다운(지금)** |
| --- | --- | --- |
| 방향 | 1 | **4** (east 를 west 반전으로 만들면 실질 3) |
| 프레임/방향 | 55 | 37 (4장 참고) |
| 부착점 | 6 | 4 (슬라임은 팔다리가 없어 적다) |
| 베이스 | 5벌 | 5벌 |
| **좌표 총량** | 1,650 | **2,220** (east 생략 시 1,665) |

손으로 찍기는 어렵다. 자동 추출이 필요하다.

### 3-2. PixelLab `estimate-skeleton` — 사람에만 쓴다 **(확인됨)**

Python SDK 소스에서 직접 확인했다.

- 입력: 배경 투명 캐릭터 그림 1장 / 출력: `keypoints` 배열, 각 원소 `{x, y, label, z_index}`
- `x`,`y` 는 **0~1 정규화 float**, `z_index` 는 앞뒤 순서
- `label` 은 **18종 고정 humanoid**: `NOSE, NECK, RIGHT/LEFT SHOULDER, RIGHT/LEFT ELBOW, RIGHT/LEFT ARM(손목), RIGHT/LEFT HIP, RIGHT/LEFT KNEE, RIGHT/LEFT LEG(발), RIGHT/LEFT EYE, RIGHT/LEFT EAR`
- 요금: 64×64 **$0.00513** (크기와 거의 무관)

→ [keypoint.py](https://github.com/pixellab-code/pixellab-python/blob/main/pixellab/models/keypoint.py), [estimate_skeleton.py](https://github.com/pixellab-code/pixellab-python/blob/main/pixellab/estimate_skeleton.py)

**슬라임에는 쓸 수 없다.** `SkeletonLabel` 이 어깨·팔꿈치·무릎만 있는 **고정된 사람 관절 목록**이라 팔다리 없는 몸에는 대응하는 라벨이 없다. 억지로 부르면 아무 데나 찍힌 값이 나올 것이다(추정 — 실제로 호출해 보지는 않았다). **슬라임 앵커는 3-4 · 3-5 방식으로 직접 만들어야 한다.**

### 3-3. 베이스 여러 벌이 앵커를 공유하는 법 **(확인됨)**

`animate_with_skeleton` 시그니처:

```python
animate_with_skeleton(client, image_size, skeleton_keypoints, view, direction, ...)
#   skeleton_keypoints: list[SkeletonFrame]   # 프레임마다 keypoints 배열
#   reference_image, init_images, color_image, seed  ← 스타일·색 고정 수단
```

**포즈를 우리가 JSON 으로 넣는다.** 저장소의 `tests/skeleton_points/walk.json` 이 실제 예시이고 위 18개 라벨이 그대로 들어 있다.
→ 같은 `skeleton_keypoints` 를 사람 베이스 4~5벌에 쓰면 **프레임 단위로 같은 포즈**가 나온다. 앵커 테이블을 1벌 만들어 전부에 공유할 수 있다.
(단서: 시그니처·데이터 형식은 확인. **실제 결과물의 픽셀 정합도는 검증 안 함** — 생성 모델이라 오차는 있을 것으로 본다.)

### 3-4. 마커 픽셀 — 슬라임에 이게 맞다

부착점을 별도 레이어에 1px 특수색으로 찍고 코드가 찾는다.

- `aseprite --batch --layer "anchors" --sheet anchors.png` 로 마커 레이어만 뽑고 스캔
- 부착점 종류마다 색을 다르게 하면 한 레이어로 다 처리
- 장점: 그림 그리듯 찍으면 되고 추출은 완전 자동. rig 종류를 안 탄다
- 단점: 색 규격을 문서로 관리해야 하고, 그 색이 그림에 섞이면 깨진다

**5장에서 실제로 해 본 결과, 이 방식이 필요하다는 게 증명됐다** — 예시 이미지에서 왕관과 눈이 **똑같은 금색**을 써서 색만으로는 분리가 안 됐다. 연결 성분(connected component) 분석까지 해야 갈렸다. 마커를 따로 찍었으면 한 번에 끝날 일이다.

### 3-5. Aseprite slice — 사람이 손보는 자리 **(확인됨)**

- slice 는 **프레임별 키**를 가진다. `--data` JSON 의 `meta.slices` 에 이렇게 나온다.

```json
"slices": [{
  "name": "head_top", "color": "#0000ffff",
  "keys": [{ "frame": 0,
    "bounds": {"x": 80, "y": 0, "w": 16, "h": 16},
    "center": {"x": 2, "y": 2, "w": 12, "h": 12},
    "pivot":  {"x": 8, "y": 8} }]
}]
```

- **`pivot` 이 곧 앵커 좌표**이고 슬라이스 이름이 부착점 이름이 된다
- CLI: `--data`, `--format json-hash|json-array`, `--list-slices`, `--split-slices`, `--sheet`, `--layer`, `--split-layers`, `--tag`, `--filename-format`
→ [Aseprite CLI](https://www.aseprite.org/docs/cli/), [Slices](https://www.aseprite.org/docs/slices/)

### 3-6. 기존 툴

| 도구 | 내용 | 판단 |
| --- | --- | --- |
| [AttachPoint](https://matharoo.itch.io/attachpoint) | 프레임에 부착점을 찍고 좌표를 코드로 내보내는 전용 툴. 각도도 저장 | 발상이 같다. **GameMaker 대상**이라 그대로는 못 쓴다. 참고용 |

| [export-aseprite-file](https://github.com/dacap/export-aseprite-file) | .aseprite → JSON + PNG (Aseprite 개발자 스크립트) | 추출 계층 참고 |

### 3-7. 추천 파이프라인

```
사람  : animate_with_skeleton(같은 포즈 JSON)로 베이스 생성
        → 프레임마다 estimate_skeleton → 앵커 초안 (자동, 방향당 $0.00513)
        → 스무딩 + 정수 반올림 → Aseprite slice 로 손보정
슬라임: 마커 픽셀 레이어에 사람이 찍기 → aseprite --layer 로 추출 (완전 자동)
공통  : 앵커 JSON { rig, anim, direction, frame, point, x, y, z }
        + 앵커 JSON ↔ Aseprite slice 상호 변환 + 부착 결과 미리보기
```

## 4. 프레임 수와 M — LPC 실측 기준

### 4-1. LPC 유니버설 시트 레이아웃 **(소스에서 실측)**

`scripts/imageProcessing/sliceImages.js` 의 `cropSheet()` 를 파싱했다. 프레임 크기는 `universalFrameSize = 64` 로 못박혀 있다.

| spellcast | 7 | 4 |
| thrust | 8 | 4 |
| walk | **9** | 4 |
| slash | 6 | 4 |
| shoot | 13 | 4 |
| hurt | 6 | **1** (남쪽만) |
| climb | 6 | **1** |

## 5. K(색 변형) — 팔레트 스왑은 어디까지 되나

### 5-1. LPC 팔레트 정의 **(실측)**

`palette_definitions/` 에 재질별 색 램프가 데이터로 들어 있다. 형식은 `이름 → 6단계 hex 배열`이다.

```json
"brown":  ["#1d131e","#411E05","#4B2B13","#62351C","#744B30","#996B4A"]
"yellow": ["#301723","#5F2F25","#BA5B23","#D99431","#F3C03F","#FFE360"]
```

| 재질 | ulpc 색 수 | lpcr 색 수 | 램프 단계 |
| --- | --- | --- | --- |
| **cloth (옷)** | **24** | — | 6 |
| hair | 26 | 20 | 6 |
| body | 22 | 9 | 6 |
| metal | 8 | 7 | 6 |
| eye | 8 | 7 | **3** |
| wood | 4 | 5 | 6 |
| **all (통합)** | — | **75** | 6 |

각 조각은 `recolors` 필드로 어떤 재질·팔레트를 쓰는지 선언한다. 실제 사용 현황: `cloth` 146개, `hair` 122개, `body` 66개, `metal` 53개. 팔레트로는 `ulpc` 394개, `all.lpcr` 392개.

→ **K = 24 (옷 기본 램프) ~ 75 (통합 팔레트).** 우리가 색을 고를 필요조차 없다. 이미 화가들이 다듬어 놓은 램프다.

### 5-2. 팔레트를 어떻게 정의해야 하나

**색 대응표가 아니라 "램프 인덱스" 로 가는 게 맞다.** LPC 가 그렇게 돼 있다.

- 조각 원본은 **6단계 램프 한 벌**로만 그린다 (어두움 → 밝음)
- 색을 바꾼다 = 램프를 통째로 다른 램프로 갈아끼운다. 픽셀별 색 대응표를 만들 필요가 없다
- 이래야 명암 관계가 안 깨진다. 색 하나씩 바꾸면 그림자가 본체보다 밝아지는 사고가 난다

**64×64 픽셀아트 주의점**

- **외곽선 색은 램프에서 빼둔다.** 같이 바뀌면 실루엣이 흐려진다
- **안티에일리어싱을 쓰면 안 된다.** 램프에 없는 중간색이 생기면 스왑에서 누락된다. 예시 이미지도 27색·22색·18색으로 아주 적다 (5-3)
- **정확 일치(exact match)로 매핑하고, 램프에 없는 색이 나오면 오류로 잡아야 한다.** 조용히 넘어가면 나중에 색 하나가 안 바뀐 채로 출시된다
- 눈처럼 3단계짜리는 램프 길이가 달라 따로 관리해야 한다 (LPC 도 eye 만 3단계다)

### 5-3. 예시 이미지 실측 — 우리 아트가 이 조건을 만족하는가

`Docs/Example/` 3장을 픽셀 단위로 뜯어봤다.

| 파일 | 캔버스 | 색 수 | 불투명 픽셀 |
| --- | --- | --- | --- |
| Front.png | 64×64 RGBA | 27 | 1,335 |
| Left.png | 64×64 RGBA | 22 | 1,240 |
| Back.png | 64×64 RGBA | 18 | 1,362 |

- 색이 18~27개로 아주 적다 → **램프 방식에 그대로 맞는다.** 좋은 출발이다
- 몸 = 흰색/회색 계열 (`#FFFFFF`, `#FFFEF9`, `#E2E2E2`, `#CCCCCC`, `#B3B3B3`), 왕관 = 금색 계열 (`#FFD500`, `#EDC800`, `#E0BD00`, `#BE9F00`), 외곽선 = 검정
- **몸과 왕관의 램프가 이미 분리돼 있다.** 몸 색만 바꾸면 왕관은 그대로 남는다 → 슬라임 색 변형 K 가 바로 된다
- **다만 왕관 금색과 눈 금색이 같은 색이다.** 색만으로는 둘을 못 가른다 (3-4 에서 지적한 문제)

### 5-4. 미리 굽기 vs Unity 런타임 셰이더 — **런타임 셰이더 추천**

| | 미리 굽기 (툴이 PNG 생산) | 런타임 LUT 셰이더 |
| --- | --- | --- |
| 스프라이트 수 | M8 × K5 = 40벌 × 154 = **6,160장** | 원본 8벌 × 154 = **1,232장** + 램프 텍스처 |
| 색을 더 늘릴 때 | 다시 굽고 아틀라스 재빌드 | **공짜** (램프만 추가) |
| VRAM | 색 변형만큼 선형 증가 | 거의 안 늘어난다 |
| 비용 | 없음 | 프래그먼트에서 **dependent texture read** — 모바일에서 체감될 수 있다 |
| 런타임 색 바꾸기 | 안 된다 | 된다 |

**런타임 셰이더로 간다.** 이유는 앞서 부착 방식을 런타임으로 정한 것과 같다 — **조합 폭발을 데이터가 아니라 코드로 흡수한다.** LPC 램프가 이미 6단계 인덱스 구조라 LUT 텍스처로 그대로 옮겨진다.

단, **툴에도 미리 굽기 기능은 남긴다.** 문서용 미리보기·스토어 스크린샷·아트 검수에 필요하고, 나중에 성능 문제가 생기면 자주 쓰는 조합만 구워서 대체할 수 있어야 한다.

## 6. 40종을 어떻게 채우나 — M × K + 부착물

### 6-1. 사람 캐릭터

| 안 | M(실루엣) | K(색) | 부착물 | 코스튬 수 | 손그림 |
| --- | --- | --- | --- | --- | --- |
| **A. 실루엣 위주 (추천)** | 8 (LPC torso 80종에서 고름) | 5 (cloth 24색에서) | 0 | **40** | **0장** |
| B. 색 위주 | 5 | 8 | 0 | 40 | 0장 |
| C. 부착물 섞기 | 4 | 5 | 2 (모자·날개) | 4×5×2 = **40** | 0장 (LPC headwear 128종) |
| D. 전부 직접 | 8 | 5 | 0 | 40 | **1,232장 — 불가능** |

→ **A 또는 C. 어느 쪽이든 손그림 0장이다.** 실제로는 LPC 상의 80종 × 색 24종 = 1,920가지가 이미 가능하므로, 40종은 "고르는" 문제이지 "만드는" 문제가 아니다.

### 6-2. 슬라임 캐릭터 — 여기가 진짜 작업이다

LPC 밖이라 기성품이 없다. 대신 **팔다리가 없어 앵커가 아주 잘 통한다.**

| 안 | 몸 실루엣 | 몸 색 K | 강체 부착물 | 코스튬 수 | 손그림 |
| --- | --- | --- | --- | --- | --- |
| **추천** | 1 (통짜, 이미 있음) | 8 | 5 (왕관·모자·뿔·날개·리본) | 8 × 5 = **40** | **부착물 5장 × 4방향 = 20장** |
| 부착물 늘리기 | 1 | 5 | 8 | 40 | 32장 |
| 몸 모양도 바꾸기 | 3 | 4 | 3 | 36 | 3×154 + 12×4 = **510장 — 힘들다** |

→ **슬라임 코스튬은 "부착물 1장 × 4방향 + 몸 색"** 으로 간다. 손그림 20~32장이면 끝난다.
→ **몸 실루엣은 1종으로 못박는 게 좋다.** 늘리는 순간 154장짜리 층 그림이 되살아난다.

### 6-3. 예시 이미지에서 뽑아낸 실제 앵커값

Front / Left / Back 3장을 재서 왕관(강체 부착물)과 몸을 분리했다. 왕관과 눈이 같은 금색이라 **연결 성분 분석**으로 갈랐다.

| 방향 | 몸 bbox | 왕관 bbox | 왕관 중심 | **앵커** (몸 상단중앙 `(31.5, 16)` 기준) |
| --- | --- | --- | --- | --- |
| Front | x11..52, y16..50 | x42..55, y12..25 | (48.5, 18.5) | **dx = +17.0, dy = +2.5** |
| Left | x11..52, y16..50 | x29..41, y13..26 | (35.0, 19.5) | **dx = +3.5, dy = +3.5** |
| Back | x11..52, y16..50 | x8..21, y10..25 | (14.5, 17.5) | **dx = −17.0, dy = +1.5** |

여기서 나온 사실들:

- **몸 bbox 가 3방향 모두 완전히 같다** (`x11..52, y16..50`). baseline Y=50, 중심 X=31.5 가 이미 지켜져 있다. **규격 검사를 통과하는 아트다.** 좋은 출발점이다
- **Front 와 Back 의 dx 가 정확히 ±17 로 대칭**이다 → 왕관을 머리 한쪽에 비스듬히 씌운 것이고, 앞뒤에서 좌우가 뒤집혀 보이는 게 맞다. **Right 방향은 Left 를 좌우반전해서 만들 수 있다**(아트가 대칭이라는 전제)
- 왕관 크기는 14×14 (Front/Back), 13×14 (Left) → 부착물 조각을 **16×16 셀**로 규격화하면 딱 맞는다
- 눈은 11×11 두 개, Front (19,39)·(44,39) / Left (23,39) 하나 / Back 없음 → 눈도 부착물로 뺄 수 있다(표정 교체)
- 방향별로 왕관이 몸 뒤로 가는지 앞으로 오는지 달라지므로 **앵커에 `z`(sorting order)가 반드시 들어가야 한다**. Back 에서는 왕관 일부가 몸에 가려야 자연스럽다

## 7. PixelLab — 줄어든 역할

역할은 **베이스 4~5벌 + 아이템 낱장 그림**이다. 40벌 대량 생성이 아니다.

### 7-1. 탑다운 4방향 지원 **(확인됨)**

MCP 문서 기준.

- `create_character`: `view` = **`low top-down`(기본, RPG 각도)** / `high top-down` / `side` / `oblique`
- `n_directions` = **4 또는 8**
- `body_type` = `humanoid` / **`quadruped`** (템플릿: bear, cat, dog, horse, lion)
- `size` 최대 128 (standard/pro) · 256 (v3)
- `animate_character`: `directions` 목록으로 **south, north, east, west** 지정 가능, `frame_count` 4~16 짝수(v3), `mode` = template/v3/pro
- 확인된 애니메이션 템플릿은 **Walk · Running · Thrust · Cast spell** 넷뿐이다. idle·jump 는 `action_description` 자유 텍스트나 스켈레톤 입력으로 해야 한다

→ **탑다운 4방향은 정식 지원된다.** 방향별 스켈레톤 추출도 방향별 프레임에 `estimate_skeleton` 을 부르면 되므로 문제없다(비용만 4배).

### 7-2. 슬라임은 어떻게 뽑나

`body_type` 에 **blob·amorphous 같은 값이 없다.** humanoid 아니면 quadruped 뿐이다.
→ 슬라임은 **참조 이미지 경로**로 간다. `create_character_v3` 에 `reference_image_url` 을 주거나, `POST /v2/rotate`($0.01057) · `generate-8-rotations-v3`($0.0337) 로 이미 있는 Front.png 를 회전시킨다. **이 경로가 실제로 잘 되는지는 확인 못했다.**

### 7-3. 요금 **(확인됨, 64×64 기준)**

| 엔드포인트 | 용도 | USD |
| --- | --- | --- |
| `create-character-with-4-directions` | **탑다운 4방향 캐릭터** | $0.0122 |

**비용은 논점이 아니다.** 제약은 일관성이다.

### 7-4. 일관성 — 무엇이 되고 무엇이 안 되나 **(중요)**

| 되는 것 (확인된 파라미터) | 하는 일 |
| --- | --- |
| `skeleton_keypoints` | **포즈 완전 고정.** 가장 강한 수단 |
| `reference_image_url` / `_base64` | 생김새 그대로 옮기기 |
| `style_character_id` | 기존 캐릭터 스타일 기준 (**pro 모드만**) |
| `color_image` | 팔레트 강제 |
| `use_color_palette_from_reference` | 원본 색에 스냅 |
| `proportions` | 체형 비율 JSON |
| `seed` | 결정적 재생성 |

**안 되는 것**: **발바닥 baseline Y · 픽셀 키 · 프레임 안 위치를 못박는 파라미터는 없다.** `size` 와 `proportions` 로 근사할 뿐이다.

**그래서 우리 코드가 후처리로 어디까지 맞출 수 있나** (구체적으로)

| 문제 | 후처리로 되나 | 방법 |
| --- | --- | --- |
| baseline Y 어긋남 | **된다** | 알파 바운딩박스 최하단 Y 를 찾아 프로필의 `baseline_y`(예시 아트는 50)로 평행이동 |
| 좌우 중심 어긋남 | **된다** | bbox 중심 X 를 31.5 로 평행이동 |
| 캐릭터 키 다름 | **반만 된다** | 재서 목표치와 다르면 ① 시드 바꿔 재생성 ② 정수배 스케일. **비정수배 스케일은 격자가 깨지므로 금지** |
| 색이 램프 밖으로 나감 | **된다** | 램프에 최근접 색으로 스냅 + 램프 밖 색 개수를 리포트 |
| 색 수가 너무 많음 | **된다** | 색 수 상한(예: 32색) 검사, 넘으면 반려 |
| **체형·실루엣이 다름** | **안 된다** | 사람 손으로 고르거나 다시 뽑는 수밖에 없다 |
| **그림체가 흔들림** | **안 된다** | `reference_image` · `seed` 로 줄일 뿐 없앨 수 없다 |

→ **정렬·색은 코드로 해결된다. 실루엣과 그림체는 안 된다.** 그래서 베이스는 4~5벌로 적게 잡고 사람이 골라야 한다. 이 판단이 "M 을 PixelLab 으로 늘리자"는 안을 막는다 — **실루엣 종류를 늘릴수록 흔들림이 그대로 늘어난다.**

## 8. Unity 대응

### 8-1. 부착은 런타임 (앞 결론 유지)

| 방식 | 스프라이트 수 |
| --- | --- |
| 미리 굽기 | 부착물 40종 × 154프레임 = **6,160장**, 3칸 동시착용이면 조합 폭발 |
| **런타임 부착** | 부착물 **40장 × 4방향 = 160장** + 앵커 JSON |

**구현**: 스크립트 하나가 현재 애니메이션 이름 + 프레임 인덱스 + 방향으로 앵커 JSON 을 조회해 자식 `localPosition` 과 `sortingOrder` 를 세팅한다. 클립은 베이스용 1벌만 있으면 되고 코스튬이 늘어도 클립은 안 는다.

**주의점 3가지**

1. 애니메이션 클립에 위치를 키잉한다면 **탄젠트를 `Constant`** 로. 보간되면 서브픽셀로 흔들린다. (Unity 공식 문서가 Sprite Resolver 에 대해 같은 주의를 준다 — 문자열 해시가 보간되면 스프라이트를 못 찾는다)
2. 좌표는 **정수 픽셀로 반올림**해 PPU 격자에 스냅
3. **`sortingOrder` 를 프레임마다 바꾼다.** 슬라임 Back 방향에서 왕관이 몸에 가려야 하는 것처럼, 앞뒤 순서가 방향·프레임에 따라 바뀐다

### 8-2. 사람 캐릭터는 LPC 층 그대로

층 하나 = GameObject 하나(SpriteRenderer + SpriteResolver), `zPos` 를 `Order in Layer` 로 고정. 클립은 **Label 만 키잉**하면 옷·색이 뭐든 한 벌로 돈다. 옷 갈아입기 = Sprite Library Asset 교체.

### 8-3. 색은 런타임 LUT 셰이더 (5-4)

### 8-4. 성능

부착물·층 수만큼 드로우콜이 는다. **Sprite Atlas 하나로 묶으면 배칭된다** (추정 — 실측 안 함). 셰이더 팔레트 스왑은 dependent texture read 비용이 있어 모바일이면 재봐야 한다.

## 9. OGA-BY 라이선스 — 써도 되나

### 9-1. 조건

- OGA-BY 3.0 / 4.0 은 **복제·재배포·변형·2차창작을 상업적 용도 포함 어떤 목적으로도 허용**하고, 의무는 **원작자 표기(attribution)** 하나다
- **share-alike 의무가 없다.** 우리 게임 코드를 공개할 필요가 없다
- CC-BY 의 **anti-DRM 조항을 피하려고 만들어진 라이선스**다. 그래서 Apple App Store 같은 DRM 붙는 스토어에 낼 수 있다 — 상업 게임에는 오히려 CC-BY 보다 유리하다
- → [OGA FAQ](https://opengameart.org/content/faq), [LPC 포럼 스레드](https://lpc.opengameart.org/forumtopic/commercial-usage-of-oga-assets-and-more)

### 9-2. 허용 여부가 만드는 실제 차이 **(실측)**

같은 애니메이션을 지원하는 조각이 몇 개나 남는지 세었다.

| 애니메이션 | 전체 | **OGA-BY 허용 시** | CC 계열만 (OGA-BY 제외) |
| --- | --- | --- | --- |
| walk | 571 | **462** | 180 |
| run | 489 | **397** | 141 |
| jump | 491 | **398** | 141 |
| idle | 536 | **439** | 167 |
| sit | 492 | **399** | 141 |

그리고 분류별로 CC0 만 고집하면 이렇게 된다.

| 분류 | 전체 | CC0 만 |
| --- | --- | --- |
| torso (상의) | 102 | **2** |
| legs (하의) | 22 | **0** |
| feet (신발) | 17 | **0** |

**결론: OGA-BY 를 허용해야 한다.**
- 허용하면 657종 중 **525종(80%)**, run 기준 397종을 쓸 수 있다
- 금지하면 run 141종으로 **2.8배 줄고**, CC0 만 고집하면 **하의·신발이 0종이라 옷을 못 입힌다**
- 대가는 크레딧 화면에 작가 이름을 적는 것뿐이다. `credits` 필드에 작가·라이선스·출처가 다 들어 있어 **크레딧 문서 자동 생성이 된다**

> LPC 조각들은 대부분 **다중 라이선스**다(예: `["OGA-BY 3.0", "CC-BY-SA 3.0", "GPL 3.0"]`). 이건 **셋 중 하나를 고르는 것**이므로 OGA-BY 3.0 을 택하면 share-alike·GPL 의무는 지지 않는다. **다만 다중 라이선스 해석은 법률 판단이므로 최종 확인은 사용자 몫이다.**

## 10. 아직 확인 못한 것

- **`estimate-skeleton` 의 64×64 실제 정확도.** 탑다운 위/아래 방향에서 팔다리가 몸에 겹칠 때 관절을 제대로 찍는지, 프레임 간 떨림이 얼마나 되는지 → **실제로 돌려봐야 안다**
- **슬라임에 `estimate-skeleton` 을 부르면 어떻게 되는지** — 라벨이 전부 사람 관절이라 안 될 것으로 보지만 실제 호출은 안 해 봤다
- **`animate_with_skeleton` 에 같은 포즈를 넣었을 때 베이스 여러 벌의 픽셀 정합도**
- **PixelLab 으로 슬라임 4방향을 뽑는 경로**(`rotate` / `generate-8-rotations-v3` / `reference_image`)가 실제로 쓸 만한지
- **PixelLab 애니메이션 템플릿 전체 목록** — 문서에 Walk·Running·Thrust·Cast spell 넷만 보인다
- **PixelLab 구독 등급별 월 크레딧·정가·이월 여부**, API 종량제와 구독의 관계 → 가격 페이지가 JS 렌더링이라 자동 조회 불가. `get_balance` 로 확인 가능. (2차 출처: 최대할인 tier1 $9/월, tier2 $22/월)
- **Stardew Valley 위키 원문** — 403 으로 자동 조회가 막혀 검색 요약으로만 확인했다. 셔츠 오프셋 구조는 **2차 확인이 필요하다**
- LPC 의 `combat_idle` 이 `idle` 과, `emote` 가 `sit` 과 같은 행을 쓰는데 **별개 블록인지 별칭인지 확인 못했다**
- LPC 다중 라이선스(`OR` 선택)의 **법적 해석** — 통설은 선택 가능이지만 법률 자문은 아니다
- Unity 팔레트 스왑 셰이더의 **실제 모바일 성능** (dependent texture read 비용)
- 예시 이미지의 Right 방향이 **정말 Left 좌우반전으로 충분한지** (아트가 완전 대칭인지 확인 못함. 왕관이 비스듬해서 반전하면 반대쪽으로 기운다)

## 11. 사용자에게 물어볼 것

1. **OGA-BY 를 허용하나?** 이게 최우선이다. 금지하면 하의·신발이 0종이라 **사람 코스튬 계획 자체가 성립하지 않는다.** 대가는 크레딧에 작가 이름 넣기뿐이고, 자동 생성된다.
2. **사람 코스튬 40종을 LPC 기성품에서 고르는 걸로 해도 되나?** 그러면 손그림 0장이다. 대신 그림체가 LPC 로 고정된다. 슬라임 예시 아트(흰색·적은 색·둥근 외곽선)와 LPC 화풍이 섞여도 괜찮은지가 관건이다.
3. **슬라임 몸 실루엣은 1종으로 못박아도 되나?** 늘리면 154장짜리 층 그림이 되살아난다. 대신 부착물과 색으로 40종을 채운다.
4. **부착물 몇 종을 그릴 건가?** 슬라임 쪽 손그림은 여기서만 나온다. 5종 × 4방향 = 20장이면 감당된다.
5. **애니메이션 세트를 확정하자.** 4-2 의 8종·37프레임/방향·총 154장 안이 괜찮은지. 여기가 전체 작업량을 정한다.
6. **east 방향을 west 좌우반전으로 만들어도 되나?** 되면 앵커 데이터가 4방향 → 3방향으로 준다. 단 왕관처럼 비대칭인 장식은 반전하면 반대쪽으로 기운다.
7. **앵커 편집을 Aseprite slice 로 할지, 마커 픽셀로 할지.** 슬라임은 마커 픽셀이 편해 보인다(왕관·눈이 같은 색이라 색 자동 분리가 실패했다).
8. **PixelLab 계정에서 `get_balance` 를 한 번 봐 달라.** 월 크레딧과 API 종량제 관계를 알아야 예산이 선다.
