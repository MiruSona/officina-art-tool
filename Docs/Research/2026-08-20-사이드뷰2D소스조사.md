# 사이드뷰 2D 소스 조사

대상: 시점이 **사이드뷰 횡스크롤 플랫포머**, 캔버스 **64×64** 로 확정된 뒤의 에셋 소스 · 파이프라인 재검토.
앞 조사(`2026-08-19-2D그림툴조사.md`)의 후속이다. 앞 문서는 그대로 두고 이 문서가 덮어쓴다.

## 바뀐 추천안

1. **여러 팩을 모아 조합하는 방식은 버린다.** 사이드뷰에는 LPC 같은 공통 규격이 **없다**. 팩마다 프레임 크기(18·32·48·50×37·64×128·80×64)와 그림체가 다 달라서 섞이지 않는다.
2. **베이스 1벌을 고르고 그 위에 전부 쌓는 "단일 베이스" 방식으로 간다.** 베이스는 ① CC0 팩 하나를 골라 64로 맞추거나 ② PixelLab 로 `view=side`, `size=64` 로 뽑는다. 나머지(색·장비·프레임)는 전부 코드가 만든다.
3. **사이드뷰 paper doll 은 된다. 단 조건이 붙는다.** 앞팔(near arm)을 몸통에서 떼서 별도 층으로 올려야 하고, 옷·갑옷 층은 **프레임마다 그려야 한다**. Terraria · Starbound 가 실제로 이렇게 한다.
4. **무기·손에 드는 물건은 층이 아니라 "손 앵커" 로 붙인다.** 프레임마다 손 좌표 · 회전 · 앞뒤 순서를 JSON 에 적어두고 무기 그림 1장을 얹는다. 비용이 층 방식의 1/N 이다. 여기가 툴이 제일 값어치를 내는 지점이다.
5. **스켈레탈(뼈)로 갈 필요 없다.** 64×64 픽셀아트를 뼈로 돌리면 격자가 깨진다. Unity 의 Sprite Library / Sprite Resolver 는 시점과 상관없이 그대로 유효하다.

## 2. 64×64 는 현실적인가

**결론: 목표 크기로는 문제없다. 단 "64×64 사이드뷰 소스가 많다" 는 기대는 버려야 한다.**

근거:

- 무료 사이드뷰 팩의 프레임 크기는 제각각이다. 확인한 것만 18×18(Kenney) · 48×48(ZeggyGames) · 64×64(Gimbo) · 64×128(retraissance) · 80×64(GandalfHardcore). **표준이 없다.**
- 사이드뷰 캐릭터는 세로가 가로보다 길다. 그래서 실무에서는 정사각형 64×64 보다 **64×64 셀 안에 키 40~50px 짜리 캐릭터를 넣거나**, 아예 세로로 긴 프레임(64×128)을 쓴다. 64×64 를 셀 크기로 잡되 **캐릭터 실제 키는 40~48px 로 정하는 게 안전하다.** 공격 이펙트가 프레임을 넘칠 때만 128×128 오버사이즈 셀을 따로 둔다 (LPC 도 큰 무기에 같은 방식을 쓴다).
- PixelLab 은 64×64 를 정식 지원한다 (캐릭터 size 16~256, 애니메이션 캔버스 16/32/64/128/256). **크기 때문에 막히는 일은 없다.**

**제안**: 캔버스 64×64 유지. 여기에 규격 두 개를 더 못박는다 — ① 캐릭터 키 40~48px, ② 발바닥이 닿는 기준선(baseline) Y 좌표 고정. 이 두 개가 없으면 나중에 장비가 다 어긋난다.

## 3. 사이드뷰 paper doll — 되는가

**결론: 된다. 하지만 탑다운처럼 "조각을 그냥 겹치면 되는" 수준은 아니다.**

### 3-1. 왜 어려운가

탑다운은 몸이 정면이라 앞팔이 몸통을 크게 안 가린다. 사이드뷰는 옆에서 보므로 **앞팔이 항상 가슴을 가로지른다.** 옷을 그냥 몸통 위에 얹으면 옷이 앞팔을 덮어버린다.

### 3-2. 실제 게임이 푸는 방법 (확인된 사례)

- **Starbound**: 옷 스프라이트를 **앞팔(front arm) 레이어와 몸통 레이어 사이**에 그린다. 즉 캐릭터가 `뒤팔 → 몸통 → 옷 → 앞팔 → 손물건` 순서의 층으로 되어 있다. 앞팔은 처음부터 몸통과 별개 그림이다. ([Chucklefish 포럼 · Starbounder 위키](https://starbounder.org/Modding:Items/Armors))
- **Terraria**: 방어구를 `Armor_Head_*` · `Armor_*`(몸통+팔) · `Armor_Legs_*` 세 장으로 나누고, **각 장이 몸통 애니메이션과 같은 프레임 격자를 쓴다.** 프레임 번호만 맞추면 알아서 붙는다. ([정리 문서](https://deepwiki.com/thecakeisalie05/Terraria/4.3-character-and-equipment-sprites))

두 사례가 말하는 건 같다. **사이드뷰 paper doll 의 정답은 "부위별 층 + 층마다 전체 애니메이션" 이다.**

### 3-3. 그래서 우리가 지켜야 할 규칙

```
층 순서 (아래 → 위)
  0  뒤팔 · 뒤다리
  1  몸통 + 머리 (베이스)
  2  옷 · 갑옷
  3  머리카락 · 모자
  4  앞팔 · 앞다리        ← 여기가 사이드뷰의 핵심
  5  손에 든 물건          ← 층이 아니라 앵커로 붙임
```

- **비용의 진실**: 2번(옷·갑옷) 층은 **애니메이션 프레임 수만큼 그려야 한다.** 걷기 8프레임이면 옷도 8장이다. 조각 1개 = 그림 1장이 아니다. 이걸 모르고 시작하면 작업량이 터진다.
- **그래서 실제 전략은 두 갈래로 나뉜다.**
  - **싼 쪽 (먼저 한다)**: 팔레트 스왑. 그림을 한 장도 안 그리고 색만 바꿔 수십 벌을 만든다. 툴이 제일 먼저 만들 기능.
  - **비싼 쪽 (나중)**: 옷·갑옷 층. 프레임마다 그려야 하므로 종류를 적게 잡는다.
  - **중간 (가성비 최고)**: 손 앵커 방식. 무기 그림 1장 + `프레임별 {x, y, 회전, 앞/뒤}` JSON. retraissance 베이스가 이걸 전제로 그려져 있다. 무기 100종을 만들어도 프레임 부담이 없다.

### 3-4. 스켈레탈로 가야 하나

**아니다.** 픽셀아트를 뼈로 돌리면 각도가 붙는 순간 격자가 깨져 지저분해진다(RotSprite 같은 회전 알고리즘으로 완화는 되지만 완전하지 않다). Unity 공식 2D Animation 샘플조차 픽셀아트 버전은 프레임 애니메이션으로 만들어져 있다. 스켈레탈은 캐릭터가 수십 마리 동시에 나와 메모리가 문제될 때 다시 보면 된다.

## 4. Unity 쪽 — Sprite Library 는 사이드뷰에서도 유효한가

**유효하다. 시점과 아무 상관 없는 기능이다.**

Sprite Library Asset 은 `Category`(예: `앞팔`) 와 `Label`(예: `walk_03`) 로 스프라이트를 등록해두는 표일 뿐이고, Sprite Resolver 가 런타임에 그 표에서 골라 꽂는다. 탑다운이든 사이드뷰든 똑같이 돈다.

**우리 구조에 맞는 쓰는 법**

- 층 하나 = GameObject 하나 (SpriteRenderer + SpriteResolver). 3-3 의 층 순서를 `Order in Layer` 로 고정한다.
- 애니메이션 클립은 **Label 만 키로 찍는다.** (`walk_01` → `walk_02` → …) 그러면 클립 한 벌로 모든 옷·모든 색이 돌아간다.
- 옷을 갈아입히는 건 **Sprite Library Asset 을 통째로 바꾸는 것**이다. 클립은 손 안 댄다.
- Sprite Resolver 여러 개가 공통 부모의 Sprite Library 하나를 같이 볼 수 있다. ([공식 문서](https://docs.unity3d.com/Packages/com.unity.2d.animation@9.0/manual/ex-sprite-swap.html))

**앞 조사에서 적은 주의점은 그대로 유효**하다 — 한 Animator Controller 안에서 `SpriteRenderer.sprite` 직접 교체와 `SpriteResolver` 교체를 섞지 말 것.

**스켈레탈 도구 비교 (참고용, 지금은 안 쓴다)**

| 도구 | 상태 | 판단 |
| --- | --- | --- |
| Unity 2D Animation (PSD Importer + Skinning Editor + IK) | 엔진 기본 | 쓴다면 이것. 단 픽셀아트엔 부적합 |
| DragonBones | **LoongBones 로 이름이 바뀌고 유료 플랜이 생겼다는 이야기가 있다. 2차 출처(블로그)뿐이라 확인 못함.** C++ 런타임 저장소도 최근 활동이 안 보인다 | 권하지 않음 |
| Spine | 유료 상용 | 범위 밖 |

## 5. perfectPixel · PixelLab 은 사이드뷰에서도 유효한가

### perfectPixel — **그대로 유효**

하는 일이 "격자가 어긋난 이미지를 진짜 픽셀 격자에 맞추기" 라서 시점과 무관하다. AI·GPU 도 안 쓴다(MIT). PixelLab 이 뽑은 베이스를 정리하는 자리에 그대로 둔다.

### PixelLab — **유효하다. 사이드뷰를 정식 지원한다.**

MCP 문서에서 확인한 것:

- **캐릭터 view 옵션에 `side` 가 있다.** 설명은 "eye-level profile"(눈높이 옆모습). 다른 값은 `low top-down`(기본, RPG 각도) · `high top-down` · `oblique`.
- **크기**: 캐릭터 `size` 16~256px (기본 48). 애니메이션 캔버스는 16 / 32 / 64 / 128 / 256 지원. **64×64 정식 지원.**
- **애니메이션**: `animate_character` (mode: template · v3 · pro), 프레임 4~16(짝수). 웹 에디터에는 뼈대를 잡아 애니메이션을 만드는 `Animate with skeleton` 과 텍스트로 만드는 `Animate with text` 도 있다.
- **사이드뷰 타일셋 전용 툴도 있다** — `create_sidescroller_tileset`.
- 생성은 여전히 **비동기**(job ID → 보통 2~5분). "요청 → 폴링 → 다운로드" 3단계 구조는 그대로.

**주의점 2가지**

1. `n_directions` 는 4 또는 8 이다. 사이드뷰 플랫포머는 방향이 좌·우 하나뿐인데, **1방향만 뽑는 옵션이 있는지 확인 못했다.** 4방향으로 뽑고 east 만 쓰고 버리는 낭비가 생길 수 있다.
2. `Animate with skeleton` 이 **API·MCP 로도 되는지 확인 못했다.** 문서상 웹 에디터 기능으로만 설명돼 있다. API 로는 `animate_character` 만 확실하다.

**자리**: 앞 조사와 같다. **베이스 1벌 뽑을 때만** 쓰고, 그 뒤 색 변형 · 장비 조합 · 층 분리는 전부 코드가 한다.

## 6. 고쳐 쓴 파이프라인

```
[지시 JSON]  { base:"hero64", 옷:"tunic", 색:"lospec/nyx8", 무기:"sword_01", 상태:["idle","walk","jump"] }
      ↓
[카탈로그]  조각 목록 · 층 순서 · 라이선스 · 프레임 규격 · 손 앵커 좌표
      ↓
[결정적 합성 코드 (Pillow)]
   1) 층 겹치기   뒤팔 → 몸통 → 옷 → 머리 → 앞팔
   2) 손 앵커     프레임별 {x,y,회전,앞뒤} 로 무기 1장 붙이기
   3) 팔레트 스왑
   4) 규격 검사   프레임 크기 · baseline Y · 캐릭터 키
      ↓  (원본 없을 때만) PixelLab view=side, size=64 → perfectPixel 로 격자 정리 → 카탈로그 등록
[스프라이트시트.png + manifest.json]
      ↓
[Unity]  층별 GameObject + Sprite Library Asset → 클립은 Label 만 키잉
```

앞 조사와 달라진 곳은 **① 층 순서에 앞팔/뒤팔이 들어간 것, ② 손 앵커 단계가 새로 생긴 것, ③ 규격 검사에 baseline 이 추가된 것** 셋이다.

**툴 만드는 순서 제안** (싼 것부터)

1. 팔레트 스왑 + 스프라이트시트 굽기 + 규격 검사 → 그림 한 장 안 그리고 결과가 나온다
2. 손 앵커로 무기 붙이기 → 가성비 최고
3. 앞팔/뒤팔 분리 + 옷 층 → 여기서부터 손그림 비용이 든다

## 7. 아직 확인 못한 것 / 사용자에게 물어볼 것

**확인 못한 것**

- Pixel Frog · ansimuz · Kenney Platformer Characters 의 **정확한 프레임 크기**. 페이지에 안 적혀 있어 실제로 받아봐야 안다.
- Kenney Modular Characters 에 **애니메이션이 있는지**. 정면 그림으로 보여 플랫포머용은 아닌 듯하나 실물 확인 못함.
- LPC 에셋 중 CC0 · CC-BY 만 남기면 몇 개가 남는지 (앞 조사에서도 미실측, 이번에도 못 했다).
- PixelLab 이 **1방향(옆모습만) 생성**을 지원하는지.
- PixelLab 의 **`Animate with skeleton` 이 API·MCP 로 되는지.**
- PixelLab 생성물의 **상업 이용 조건** — 앞 조사에 이어 여전히 미확인. 계정 로그인이 필요하다.
- DragonBones → LoongBones 리브랜딩과 유료화가 사실인지 (2차 출처뿐).
- itch.io 목록 페이지는 자동 조회가 막혀 있어(403) **CC0 사이드뷰 팩 전수 조사는 못 했다.** 검색으로 잡힌 것만 정리한 결과다.

**물어볼 것**

1. **베이스를 어느 쪽으로 갈까?**
   (가) CC0 팩 하나(retraissance)를 골라 그림체를 거기 맞춘다 — 공짜, 확실, 대신 그림체 선택권 없음
   (나) PixelLab 로 원하는 그림체의 베이스를 뽑는다 — 자유롭지만 생성형 AI 를 한 번 쓴다
2. **캐릭터 키를 40~48px 로 못박아도 되나?** 64×64 셀은 유지하되 실제 키를 정해야 장비가 안 어긋난다.
3. **OGA-BY 라이선스를 허용할까?** LPC 확장 애니메이션(run · jump · idle · sit)이 OGA-BY 3.0/4.0 이다. CC-BY 처럼 출처만 밝히면 되고 share-alike 는 없다. 규칙에 CC0·CC-BY 만 적혀 있어 판단이 필요하다.
4. **CC-BY 를 실제로 쓸 건가?** 쓴다면 ZeggyGames 의 `.ase` (부위 색 구분 레이어)가 층 분리 작업의 본보기로 가장 쓸 만하다. CC0 만 고집하면 층 분리는 백지에서 시작해야 한다.
5. **옷·갑옷을 몇 종이나 만들 생각인가?** 층 방식은 종류 × 프레임 수만큼 그림이 필요하다. 5종만 넘어가도 부담이 크다. 무기는 손 앵커라 100종도 괜찮다.
6. **애니메이션 세트를 먼저 확정하자.** idle · walk · run · jump · fall · attack 6종만 잡아도 프레임이 40장 근처다. 여기가 전체 작업량을 결정한다.
