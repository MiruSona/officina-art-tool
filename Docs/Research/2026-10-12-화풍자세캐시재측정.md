# 화풍 참조 · 자세 편집 · 캐시 서버 재측정 (2026-10-12)

진행상황 「로컬 그림 모델」 절의 H3 재측정 · ⑭ H4 재시도 · ⑫ 캐시 서버 · ⑥ LoRA 경고를 한 판에 잰 기록이다.
10-08 실측(`2026-10-08-로컬그림모델무거운판실측.md`)과 같은 워크플로 · 시드 · 뒤 사슬을 썼다. 코드는 안 고쳤다.

## 결론

- **같은 조건이면 10-08 과 PNG 바이트까지 똑같다.** H3 · H4 같은 조건 네 판 모두 64px 결과와 512 날것이 10-08 파일과 md5 가 같다. 시드만 같으면 날이 달라도 같은 그림이 나온다.
- **H3 화풍 참조 : 참조 팔레트는 여전히 안 따라온다.** 참조를 「보라 몸 + 하늘색 볼 · 왕관」으로 바꿔도 통은 갈색 · 회청색 띠 그대로다. 「픽셀풍까지만 따른다」는 2단계 결론이 이번엔 특징 있는 색으로도 맞았다.
  단 **사용자가 정한 참조(게임 저장소 주인장 캐릭터)는 못 썼다** — 권한 분류기가 게임 저장소 그림을 미니PC 로 올리는 것을 막았다. 대신 ArtTool 예시 그림의 색을 바꾼 것을 썼다(아래 2절). 주인장 판은 사용자 승인 뒤 다시 돌린다.
- **H4 자세 편집 : 프롬프트에 외곽선 · 몸 부위 규칙을 더하자 오히려 나빠졌다.** 외곽선이 옅은 회색 1px 에서 **진한 남색 굵은 선**으로 바뀌었고, 시드 1000 은 몸 아래에 **없던 혹(꼬리 같은 덩이)** 이 생겼다. 글로 된 규칙만으로는 못 잡는다 — 마스크 · `reline` 후처리 쪽이 남은 길이다.
- **⑫ 캐시 켠 서버에서 같은 시드를 두 번 돌려도 결과가 비지 않는다.** 둘째 판은 62.3초 → **1.3초**, PNG 바이트는 첫 판 · `--cache-none` 판 · 10-08 판과 모두 같다. 대신 모델이 메모리에 남아 used 피크 **28.8GB**(통과선 25GB 넘음) · 스왑 78MB → 806MB 로 늘어 바로 내렸다.
- **⑥ LoRA 경고 원인 : ComfyUI 0.31 의 Flux2 키 이름 표에 「전역 modulation」 세 층이 없다.** LoRA 172 텐서 중 6개(3층)가 버려진다. ArtTool 코드 몫이 아니다(아래 4절).

## 2. H3 화풍 참조

**바꾼 것 : 참조 그림 하나.** 10-08 은 흰 덩어리 캐릭터(ArtTool `Example/Front.png`)라 색이 묻어도 티가 안 났다(mem `20261008-e44cc9c0`).
사용자가 정한 참조는 게임 저장소 주인장 캐릭터였으나 미니PC 로 올리는 단계를 권한 분류기가 막았다. 그래서 같은 `Front.png` 의 **흰색 · 회색을 보라 계열로, 노랑을 하늘색으로** 바꾼 그림(`samples/arttool_heavy_front_purple512.png`)을 대신 넣었다. 모양은 같고 색만 튀게 한 것이다.

채점은 10-08 과 같다(뒤 사슬 · 날것 64px 색 수). 「참조 색 가까운 칸」은 이번에 더한 셈이다 — 정리한 16색 결과에서 불투명 칸 중 참조 색(흰색 뺌)과 RGB 각 칸 차이가 모두 40 이하인 칸의 비율.

## 3. H4 자세 편집

**바꾼 것 : 프롬프트 끝에 규칙 글 두 문장.** 10-08 저녁 사용자 판정(mem `20261008-9b31129d`)이 짚은 실패는 「외곽선 굵기 · 모양이 바뀌고 손이 갑자기 생긴다」였다. 그 둘을 겨냥해 이 글을 더했다.

> Outline rule: keep the outline exactly 1 pixel thick and the same dark color as the reference, do not thicken or smooth it. Do not add or remove any body parts: no new hands, arms, legs or accessories that are not in the reference.

참조 그림 · 워크플로 · 시드는 10-08 과 같다. 「같은 조건」 두 판은 비교 기준으로 다시 돌렸다.

- **판단 : 글 규칙은 접는다.** ⑭ 의 남은 두 갈래 — 바꿀 자리를 마스크로 한정 · `reline` 으로 외곽선을 한 색으로 되돌리는 후처리 — 와 주인장 캐릭터 참조로 다시 본다.

## 4. ⑥ klein LoRA 경고

klein 내장 본보기(`klein_prop.json`)로 한 판 돌리고 서버 로그를 봤다. 경고는 그대로 여섯 줄이다.

```
lora key not loaded: double_stream_modulation_img.linear.lora_A.weight   (… lora_B 도)
lora key not loaded: double_stream_modulation_txt.linear.lora_A.weight   (… lora_B 도)
lora key not loaded: single_stream_modulation.linear.lora_A.weight       (… lora_B 도)
```

- LoRA 파일은 diffusers 이름 꼴로 172 텐서다. 그중 위 6개(3층)만 버려지고 나머지 166개는 들어간다.
- ComfyUI 0.31 의 Flux2 모델은 이 세 층을 `double_stream_modulation_img.lin` 처럼 **`.lin`** 으로 부른다. 그런데 diffusers 이름을 ComfyUI 이름으로 바꾸는 표(`comfy/utils.py` `flux_to_diffusers`)에 이 세 층 줄이 없다. 그래서 LoRA 쪽 `….linear` 이름을 찾을 곳이 없어 버린다.
- 이 세 층은 「전역 modulation」 — 시간 단계 정보를 모든 블록에 나눠 주는 층이다. 화풍을 그리는 본체 층은 다 들어가므로 1단계에서 「화풍엔 문제 없어 보였다」와 맞는다.
- **ArtTool 이 고칠 자리는 없다.** 제공자는 `/history` 만 보고 서버 로그는 안 보므로 이 경고를 모른다(이번 판 `report.json` 의 warnings 도 비어 있음). 고치는 길은 둘이고 둘 다 ArtTool 밖이다.
  1. LoRA 파일 키 이름을 바꾼 사본을 만든다 : `X.linear.lora_A/B.weight` → ComfyUI 가 받는 `diffusion_model.X.lin.lora_A/B.weight` 꼴. 모델 파일 일이라 이번엔 안 했다.
  2. ComfyUI 위쪽(업스트림)에 표 줄이 더해질 때까지 기다린다.
- 고쳐서 그림이 달라지는지는 안 봤다. 「세 층이 빠져서 화풍이 덜 묻는가」는 1번 사본으로 한 판 견줘야 안다.

## 5. ⑫ 캐시 켠 서버 같은 시드 재실행

절차 (1단계 문서의 기동 명령과 같은 인자에서 `--cache-none` 만 뺐다) :

1. `podman inspect comfy` 로 지금 인자 기록 → `out-1012/log/comfy_inspect.json`.
2. `podman stop comfy` → `podman run -d --name comfy-cache …`(같은 이미지 · `-v ~/imggen:/imggen` · `-p 127.0.0.1:8188:8188`, `--cache-none` 만 뺌). 12초 만에 응답.
3. H3 같은 조건 시드 1000 을 두 번.
4. `podman stop comfy-cache; podman rm comfy-cache; podman start comfy` → `/system_stats` 응답 · 기동 인자에 `--cache-none` 다시 있음 확인.

| 판 | `meta.seconds` | used 피크 | GTT | PNG md5 | 결과 비었나 |
| --- | --- | --- | --- | --- | --- |
| 캐시 1번째 | 62.3 | 28.8GB | 24.6GB | `ad8d7eb83e08` | 안 빔 |
| 캐시 2번째 | **1.3** | 26.7GB | 22.3GB | `ad8d7eb83e08` | **안 빔** |
| (견줌) `--cache-none` 오늘 · 10-08 | 47.8 · 58.7 | 21.7GB | 14.7GB | `ad8d7eb83e08` | — |

- **ComfyUI 0.31 은 모든 노드가 캐시로 넘어가도 `/history` 에 SaveImage 결과를 채워 준다.** 제공자의 `_output_images` 가 「결과 그림이 없다」로 멈출 걱정은 없다.
- 결과 그림은 서버가 새로 쓰지 않고 첫 판 파일 이름을 그대로 돌려준다. 제공자는 그 파일을 받아 오므로 PNG 는 같다.
- **메모리 : 캐시를 켜면 모델이 안 내려간다.** 첫 판 뒤 used 26.7GB 가 그대로 남았고 스왑이 78MB → 806MB 로 늘었다. 가용은 34GB 로 10GB 문턱 위였으나 「스왑이 늘면 바로 내린다」 규칙대로 둘째 판 직후 내렸다. 되돌린 뒤 스왑 80MB.
- 첫 판이 `--cache-none` 판보다 14초 느린 까닭은 안 봤다(스왑 쓰기와 겹쳤을 수 있다).

| 눈 판정 | 참고만 | 사람이 봐야 안다 |

## 8. 주인장 참조 판(추가)

같은 날 10:50 쯤, 사용자가 주인장 캐릭터 그림을 미니PC 에 직접 올린 뒤 H3 · H4 를 다시 돌렸다. **바꾼 것은 참조 그림 하나**(`arttool_heavy_owner512.png`, 125×174 를 ×2 NEAREST · 흰 바탕 512)다. 워크플로 · 프롬프트 · 시드(1000 · 1001) · 뒤 사슬 · 재는 법은 2 · 3절의 예제 참조 판과 같다. H4 는 규칙 글 없는 원래 프롬프트다.

**결론 : H3 접음은 그대로다. H4 는 색 · 옷은 지키지만 그림이 화면 밖으로 잘린다.**

- H3 : 분홍 머리 · 검은 베레모 참조를 넣어도 통은 또 갈색 · 회청색 띠다. 분홍 칸 0%.

### H3 (예제 참조 판과 나란히)

「주인장 참조 색 가까운 칸」은 2절과 같은 셈을 주인장 원본 그림(`owner_crop.png`, 흰색 뺀 40색)에 댄 것이다. 「분홍 칸」은 이번에 더한 셈이다 — 정리한 16색 결과에서 R−G ≥ 50 이고 B−G ≥ −5 인 칸의 비율. 주인장 원본은 43.8% 다.

- 「손이 갑자기 생긴다」는 안 보였다. 대신 작은 장식이 빠지고 베레모에 없던 돌기가 생긴다.
- **가장 큰 문제는 틀이다.** 옆모습을 참조보다 크게 그려 512 칸 아래로 넘친다. 스프라이트로 쓰려면 「온몸이 다 보이게」 크기를 잡아 주는 길(프롬프트 · 여백 넣은 참조 · 마스크)이 먼저다.
- 날것 64px 색이 예제 참조 판의 2~3배다. 그림이 복잡해서이고, 뒤 사슬로 16색으로 줄이면 check ok 다.
