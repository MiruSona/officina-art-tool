# PixelLab 로컬 대체 조사 (2026-10-07)

PixelLab(유료 도트 그림 생성 서비스)을 **미니PC 의 로컬 무료 모델로 바꿀 수 있나** 를 조사했다.
독립 조사자 셋(A · B · C)에게 같은 질문을 백지로 주고 각자 웹 조사만 하게 한 뒤, 메인이 셋을 견줘 이 한 장으로 합쳤다.
**셋 다 실제로 돌려 보지는 않았다.** 전부 문서 · 남의 실측 보고 근거다.

## 결론

**완전 대체는 안 된다.** 네 기능 중 새 그림(1) · inpaint(2) 는 "떨어지지만 쓸 만" 할 가능성이 있고, 8방향 회전(3) 은 전용 로컬 모델이 없어 가장 약하며, 애니메이션(4) 은 되지만 LLM 서버를 내려야 하고 매우 느리다.
현실적 목표는 **캐릭터 베이스는 PixelLab 에 남기고, 소품 · 아이콘 · 타일 · 이펙트처럼 작은 것만 로컬로** 옮기는 것이다.
**1단계(LLM 띄운 채, 기능 1 · 2)** 만 먼저 실측하고, 쓸 만하면 ArtTool `provider local` 에 붙인다. 2단계(Qwen-Edit · Wan, LLM 내림)는 1단계 결과를 보고 정한다.

→ 실측 결과는 `2026-10-07-로컬그림모델실측1단계.md` (같은 폴더). 1단계를 같은 날 돌렸다.

### 왜 조사했나

- PixelLab 크레딧을 약 2,300 gen 썼다. 계속 유료로 가기보다 로컬 · 무료로 가고 싶다.
- 미니PC : AMD Strix Halo(Ryzen AI Max+ 395, gfx1151), 통합 메모리 64GB, Ubuntu. 평소 llama.cpp LLM 서버가 약 42GB 를 쥐고 있어 **LLM 띄운 채면 ~15GB, 내리면 ~55GB** 를 쓸 수 있다.
- 상업 게임에 쓸 것이라 **라이선스가 상업 가능**해야 한다.
- 색 줄이기 · 배경 제거 · 외곽선 · 검수는 ArtTool 자체 코드가 있다. 그래서 "모델이 픽셀 단위로 완벽히 그려야 한다" 는 조건은 풀고, **512px 급으로 그린 뒤 자체 코드로 축소 · 양자화** 하는 흐름으로 판단했다.

### PixelLab 에서 쓰는 네 기능

| 번호 | 기능 | 뜻 |
| --- | --- | --- |
| 1 | 새 그림 | 글 + 화풍 참조 그림으로 캐릭터 · 소품 · 건물을 새로 그린다 |
| 2 | inpaint | 마스크 안쪽만 고치고 **마스크 밖은 한 픽셀도 안 바뀐다** |
| 3 | 회전 · 자세 | 한 캐릭터를 8방향으로 돌리거나 자세를 바꾼다 |
| 4 | 애니메이션 | 한 장에서 걷기 · idle 같은 8~16 프레임을 뽑는다 |

## 4. 기능별 판단

| 기능 | PixelLab 급 되나 | 까닭 |
| --- | --- | --- |
| 1 새 그림 + 화풍 참조 | **떨어진다** (A 는 "가깝다") | 512px 급 픽셀풍은 나온다. 하지만 24~64px 직접 출력이 없어 축소 · 재양자화에 기대고, 화풍 참조(klein · Qwen-Edit 다중 입력 · IP-Adapter)가 PixelLab style image 처럼 팔레트 · 도트 크기까지 맞춘다는 근거는 없다. 240px 건물 · 배경은 오히려 로컬이 유리할 수 있다 |
| 2 inpaint | **된다** (마스크 밖 보존은 합성 단계가 보장) | 밖은 Crop&Stitch · ImageCompositeMasked 로 비트 동일. 안쪽 품질은 1 과 같고, 격자가 깨지므로 자체 양자화 · 외곽선 정리가 뒤에 붙는다 |
| 3 회전 · 자세 | **떨어진다, 가장 큰 구멍** | 8방향을 한 캐릭터 그대로 뽑는 공개 모델이 없다. Qwen-Edit + 회전 LoRA · 4방향 시트 LoRA · OpenPose 는 전부 실사 · 일러스트 기준이고 32px 급 동일성 근거가 없다. 4방향은 손질하면 쓸 만, 대각선은 캐릭터가 바뀔 것 |
| 4 애니메이션 | **되지만 느리고 후처리 필수** | Wan 2.2 + 픽셀 LoRA 가 걷기 · idle · 공격 · VFX 로 학습됐다. 속도는 1분~34분까지 엇갈림(2절 ②). 영상이라 프레임마다 격자가 흔들려 재양자화 필요. LLM 띄운 채로는 못 돌린다 |

## 6. 메인 판정

- **셋 다 같은 말** : 실행기는 ComfyUI + kyuz0 툴박스. 24~64px 직접 생성은 없고 512px → 자체 축소. inpaint 보존은 합성 단계. 기능 3 이 가장 약함. 기능 4 는 Wan 2.2 + styly LoRA 로 되지만 LLM 내리고 매우 느림. Retro Diffusion · FLUX.1 dev · Kontext · klein 9B 제외. 화풍 참조 · 자세는 Qwen-Image-Edit-2511.
- **엇갈린 것은 2절대로 정했다** : 가벼운 판은 klein 4B 와 Z-Image-Turbo 둘 다 실측. Wan 속도는 실측 전엔 못 믿음. multiple-angles LoRA 라이선스는 미확인. ROCm 은 컨테이너 7.x. 품질 확률은 셋 다 50% 아래라 목표를 낮춘다.
- **결론** : 완전 대체는 안 된다. **1단계(LLM 띄운 채, 기능 1 · 2)** 만 먼저 실측하고, 쓸 만하면 ArtTool `provider local` 에 붙인다. 2단계(Qwen-Edit · Wan, LLM 내림)는 1단계 결과를 보고 정한다. **3(8방향) · 캐릭터 베이스는 당분간 PixelLab.**

## 7. 실측 계획

**전제** : 미니PC 게임 서버가 **꺼져 있을 때만** 한다. 1단계는 LLM 서버 띄운 채, 2단계는 LLM 서버 내리고. 밤 무인 실측은 하지 않는다(처음 띄우는 설정이라 GPU 가 멎을 수 있다).

| --- | --- | --- | --- |

## 8. 못 찾은 것 · 불확실한 것

- **klein 4B · Z-Image-Turbo 가 gfx1151 ComfyUI 에서 도는 직접 근거**가 약하다. klein 은 텍스트→3D 저장소 1건, Z-Image 는 토론 · 이슈 2건. 둘 다 계열 동작에서 추정 (A · B · C).
- **SDXL · Z-Image 의 Strix Halo 초/장 숫자**는 간접 보고뿐 ("~1.5 it/s" · "RTX 3090 의 2/3") (B · C).
- **Wan 2.2 실측치는 조건이 제각각**이라 35배 차이. 작은 해상도 소요 시간은 추정 (A · B · C).
- **ROCm 10.0 호스트**에서의 근거가 없다. gfx1151 PyTorch 가 6.14/7.0 커널에서 비결정적으로 멎는 이슈 · GPU page-fault 이슈(TheRock #2591) 가 열려 있다 (B · C).
- **Qwen-Image-Edit 에 픽셀아트를 넣었을 때** 격자 · 팔레트를 얼마나 지키는지 후기 없음. "편집 뒤 디테일 손실" 일반 후기만 (B · C).
- **multiple-angles LoRA 를 픽셀아트에 쓴 사례 없음.** 격자에서 회전이 망가질 가능성 큼 (A · C).
- **24~48px 아이콘을 축소 흐름으로 뽑은 품질 후기** 없음 (C).
- **Wan 픽셀 LoRA 의 탑다운 · 뒤보기 품질** 근거 없음. 샘플은 대부분 옆보기. 기계 움직임 사례 없음 (A · B).
- 라이선스 직접 확인 못 한 것 : dx8152 multiple-angles · Z-Image 픽셀 LoRA 일부 · nerijs pixel-art-xl · civitai Qwen 픽셀 LoRA · kyuz0 툴박스 (A · B · C).
- kyuz0 벤치는 cold run · 128GB 기기 값이라 64GB 에서 그대로 안 나올 수 있다 (B).
- Framework 포럼에 Qwen-Image 시스템 크래시 보고 있음(메모리 설정 전으로 보이나 재현 위험) (A).
- PixelLab 대 로컬 오픈 모델의 정량 비교 벤치는 없다. Retro Diffusion(유료) 대 PixelLab 것만 있다 (A).
- Sprite Sheet Diffusion 가중치 공개 여부 미확인 (A · C).
