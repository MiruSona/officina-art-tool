**한 줄 결론** : UI 툴은 새 툴이 아니라 **그림 툴의 프로필 하나**다. 다만 「앵커 뽑기」 자리에 「border 뽑기 + 폰트 굽기」가 들어간다.

## 1. UI 그림의 종류와 규격

**결론** : UI 는 9-slice 로 늘어나는 것(패널·버튼·바)과 안 늘어나는 것(아이콘)으로 딱 갈린다. 툴도 이 둘만 구분하면 된다.

| 종류 | 늘어나나 | 흔한 원본 크기 | 툴이 뽑을 것 |
| --- | --- | --- | --- |
| 패널 · 창 | 가로세로 | 16×16 ~ 48×48 | border 4값 |
| 버튼 | 가로(세로도 종종) | 16×16, 32×16 | border 4값 + 눌림/비활성 상태 |
| 슬라이더 · 프로그레스 바 | 가로만 | 8×8 ~ 32×8 | border 4값 (위아래 0) |
| 아이콘 | 안 늘어남 | **16 / 24 / 32** | 격자 자르기 + 팔레트 검사 |
| 입력 프롬프트(키·패드) | 안 늘어남 | 16×16 | 아이콘과 같음 |
| 커서 | 안 늘어남 | 16×16 | 핫스폿 좌표 |

- 크기는 **2의 거듭제곱(8·16·32·64)** 으로 맞춘다. 아틀라스에 깔끔히 들어가고 정수 배율이 나온다.
- **한 프로젝트 안에서 아이콘 크기 가족을 하나로 고정**하는 게 관례다 (예: 아이템 16, 스킬 32).
- **캔버스 64×64 는 UI 에 그대로 쓰면 안 된다.** 그건 캐릭터 프레임 값이다. UI 는 프로필에 따로 둔다.
- 광원은 **좌상단**이 표준이라, 검수에서 「위·왼쪽이 밝은가」를 볼 수 있다 (신뢰도 낮음 — 관례일 뿐 규칙은 아니다).

출처 : [SpriteGen 픽셀아트 크기 가이드](https://spritegen.io/guides/pixel-art-sizes-guide/) · [Kenney Input Prompts Pixel 16×](https://kenney-assets.itch.io/input-prompts-pixel-16) · [9-slice 스케일 설명](https://generalistprogrammer.com/tutorials/nine-slice-scaling-explained)

## 2. 9-slice

**결론** : Unity 쪽은 코드로 다 된다. 어려운 건 「border 값을 어디서 가져오나」이고, **`.9.png` 안내선을 쓰면 자동 판별에 기댈 필요가 없다.**

### 코드로 border 넣기

- `TextureImporter.spriteBorder` 는 **Vector4(x=왼, y=아래, z=오른, w=위), 단위는 픽셀**이다.
- 여러 장을 자른 시트는 `spriteBorder` 하나로 안 된다. **`ISpriteEditorDataProvider`** 로 `SpriteRect` 목록을 받아 각각의 `border` 를 채우고 `SetSpriteRects()` → `Apply()` → `SaveAndReimport()` 한다.
- 이걸 **`AssetPostprocessor` 안에서** 하면 그림을 넣는 순간 규격이 붙는다. 사람이 Sprite Editor 를 열 일이 없다 → AGENTS 10절 만족.
- 런타임에 만들 때는 `Sprite.Create(..., border)` 로 넣는다.

### 픽셀아트 9-slice 함정 (설계에서 꼭 막을 것)

| 함정 | 무슨 일이 나나 | 막는 법 |
| --- | --- | --- |
| **PPU 불일치** | Image 의 Pixels Per Unit Multiplier 가 어긋나면 테두리가 굵거나 가늘게 나온다 | 프로필의 PPU 를 툴이 굽기 때문에 고정. 검사에서 대조 |
| **모서리가 목표 크기보다 큼** | 가운데가 음수 폭이 돼 모서리가 늘어나 보인다 | 검수에서 `최소크기 = 좌+우, 상+하` 를 계산해 같이 굽는다 |
| **필터·압축** | Point 아닌 필터나 압축이면 픽셀이 뭉갠다 | Filter=Point, Compression=None 강제 |
| **UI Toolkit 동적 아틀라스** | Point 텍스처가 Bilinear 동적 아틀라스에 들어가 흐려진다 (버그 리포트 있음) | `PanelSettings` 의 `DynamicAtlasSettings` 를 필터별로 거르거나 아틀라스에서 뺀다 |
| **USS 의 `-unity-slice-scale`** | 스프라이트 PPU 가 16이면 패널 기준 100 에 대해 **16/100 = 0.16 배**가 곱해진다. 모르면 테두리가 사라진다 | 툴이 `slice-scale = 100/PPU` 를 계산해 USS 에 적는다 |
| **홀수 크기** | 정수 배율에서 반픽셀이 생겨 한 줄이 두껍게 보인다 | 원본 폭·높이를 짝수로 강제(검사 항목) |

### border 자동 뽑기

- **1순위 : `.9.png` 규약.** 원본 바깥에 1px 테두리를 두르고 검은 선으로 늘어나는 구간(위·왼쪽)과 내용 영역(아래·오른쪽)을 표시한다. 안드로이드 표준이라 에디터 지원이 많고, **그림 파일이 규격을 들고 다니는 게 핵심**이다.
- **2순위 : 자동 판별.** `Auto9Slicer`(MIT, kyubuns, 2024-08, ★279)가 하는 일이 이거다. 같은 픽셀 줄이 반복되는 행·열을 찾아 늘릴 구간으로 잡는다. 원형은 `OnionRing` 알고리즘.
  픽셀아트는 줄이 짧고 디더링이 섞여 **오판이 잦을 것으로 본다 (실측 안 함 — 신뢰도 낮음).**
- 참고 구현 : `ScaleNineSlicer`(MIT, 2026-01, ★58) 는 살아 있는 편.

출처 : [TextureImporter.spriteBorder](https://docs.unity3d.com/ScriptReference/TextureImporter-spriteBorder.html) · [Sprite Editor Data Provider API](https://docs.unity3d.com/6000.2/Documentation/Manual/sprite/sprite-editor/sprite-editor-data-provider-api.html) · [9-Slice images with UI Toolkit](https://docs.unity3d.com/2021.3/Documentation/Manual/UIE-9-slice-images-with-ui-toolkit.html) · [UI Toolkit 9-slice 흐림 이슈](https://issuetracker.unity3d.com/issues/9-sliced-sprite-assigned-as-background-in-a-ui-toolkit-visual-element-is-rendered-blurry) · [draw9patch 규격](https://developer.android.com/studio/write/draw9patch) · [Auto9Slicer](https://github.com/kyubuns/Auto9Slicer)

## 3. 폰트

**결론** : 한글 픽셀 폰트는 **갈무리**와 **네오둥근모** 둘이면 끝난다. 둘 다 OFL 1.1 이고 한글 11,172자를 다 갖고 있다.

| 폰트 | 라이선스 | 크기 | 상태 | 비고 |
| --- | --- | --- | --- | --- |
| **갈무리 (Galmuri)** | **OFL-1.1** (GitHub 확인) | 7 · 9 · 11 · 14 px | **2026-08 커밋, ★447. 살아 있음** | 닌텐도 DS 계열 그림체. 한글 11,172자 |
| **네오둥근모 (NeoDGM)** | README 는 **OFL-1.1**, GitHub 라이선스 자동판정은 `NOASSERTION` | 16px 계열 | 2026-03 커밋, ★418 | 옛 둥근모꼴 계승. **Pro(가변폭)** 도 있음. **쓰기 전에 LICENSE 원문을 직접 본다** |
| 나눔 계열 | OFL | 벡터 | — | **픽셀 폰트가 아니다.** 작은 크기에서 뭉갠다 |

- **크기가 폰트마다 정해져 있다.** 갈무리11 은 11px 에서만 또렷하다. 그래서 **UI 기준 글자 크기는 폰트가 정한다** — 그 반대가 아니다.

### TMP 설정 (툴이 굽는다)

| 항목 | 값 | 왜 |
| --- | --- | --- |
| Render Mode | **Raster Hinted** | 안티에일리어싱을 끈다. SDF 로 구우면 픽셀 폰트가 뭉갠다 |
| Sampling Point Size | **Custom = 폰트의 고유 px** (갈무리11 → 11) | 이 값과 화면 글자 크기가 어긋나면 흐려진다 |
| Padding | 4 정도 | 너무 낮으면 글자끼리 번진다 |
| Atlas 텍스처 Filter | **Point** | 기본 Bilinear 이면 흐려진다 |
| 셰이더 | **Bitmap** 계열 | 아틀라스를 그냥 텍스처로 찍는다. 외곽선·그림자 효과는 못 쓴다 |
| 화면 글자 크기 | 고유 px 의 **정수 배수만** | 13pt 같은 값을 쓰면 줄이 굵기가 들쭉날쭉해진다 |

- **한글 함정** : 11,172자를 정적 아틀라스 한 장에 못 넣는다. 방법 둘 —
  ① **동적 폰트 에셋**(쓰는 글자만 실시간으로 넣음), ② **대사 텍스트에서 쓰인 글자만 뽑아 서브셋 정적 아틀라스**.
  ②가 픽셀아트에 낫다(런타임 래스터라이즈가 없어 결과가 항상 같다). **툴이 할 일 : 텍스트 파일들을 훑어 쓰인 글자 목록을 뽑아 주기.**
- 최신 TMP 는 아틀라스가 차면 **여러 장으로 자동으로 늘린다.** 그래도 PC 4096², 모바일 2048² 를 넘기지 않게 잡는다.

## 4. 해상도 대응

**결론** : **기준 해상도 하나를 정하고 정수 배율만 허용한다.** 남는 자리는 늘리지 말고 레터박스로 버린다.

- 흔한 기준 해상도는 320×180 / 384×216 / 480×270 (다 16:9 이고 1080p 로 각각 6·5·4 배).
- **Canvas Scaler** — `Scale With Screen Size` 는 화면 비율을 맞추려고 **비정수 배율**을 만들어 픽셀이 깨진다.
  `Constant Pixel Size` 에 두고 **`scaleFactor` 를 코드가 `floor(화면높이 / 기준높이)` 로 계산해 넣는 게 안전하다.** 정수면 픽셀 완전함이 지켜진다.
- **Pixel Perfect Camera 는 월드(스프라이트)용이지 UI 용이 아니다.** `Screen Space - Overlay` 캔버스는 카메라를 안 거치므로 서로 영향이 없다. **둘의 배율을 같은 코드가 계산해 맞춰 줘야 한다** — 안 맞추면 월드 픽셀과 UI 픽셀 크기가 달라 보인다.
- UI 를 월드와 완전히 같은 픽셀 격자에 두려면 `Screen Space - Camera` + Pixel Perfect Camera 의 `Upscale Render Texture` 를 쓴다. 대신 **UI 도 저해상도로 그려져 글자가 거칠어진다.** 어느 쪽을 택할지는 설계에서 정한다.
- 창 크기가 배율의 정수배가 아니면 남는 자리가 생긴다. `Crop Frame X/Y` 로 잘라 레터박스로 둔다.

출처 : [Canvas Scaler 매뉴얼](https://docs.unity3d.com/Packages/com.unity.ugui@1.0/manual/script-CanvasScaler.html) · [Pav Creations 픽셀 퍼펙트 가이드](https://pavcreations.com/pixel-perfect-graphics-in-unity-the-practical-guide/) · [Canvas + Pixel Perfect Camera 토론](https://discussions.unity.com/t/canvas-scaling-ui-with-pixel-perfect-camera-817270/817270)

## 5. 레이아웃 — UI Toolkit 인가 uGUI 인가

**결론** : 「설정과 연결은 코드에 둔다, AI 는 인스펙터를 못 본다」(AGENTS 10절) 기준으로는 **UI Toolkit 이 확실히 낫다.** 다만 픽셀아트 함정을 툴이 대신 막아 줘야 한다.

| 기준 | uGUI | UI Toolkit |
| --- | --- | --- |
| 화면 정의가 텍스트인가 | ❌ 프리팹(YAML). **AI 가 읽고 고치기 사실상 불가** | ✅ **UXML·USS 는 사람이 읽는 텍스트** |
| 툴이 굽기 좋은가 | ❌ 프리팹을 코드로 짓는 건 장황하다 | ✅ UXML 을 파일로 뱉으면 끝 |
| 인스펙터 배선 | 필요함 (이벤트 연결) | 코드에서 `Q<Button>("id").clicked += …` |
| 그리기 비용 | 요소마다 GameObject | 가상 트리, 패널당 한 번에 그림 |
| 픽셀아트 | 사례가 많고 함정이 알려짐 | ⚠️ **동적 아틀라스 흐림 · slice-scale PPU 보정** 등 함정이 더 있음 |
| 애니메이션 | Animator·Timeline | CSS 식 전환만 |
| 기성품 | 많음 | 적음. 픽셀아트용은 사실상 없다 |

- 그래서 **툴의 산출물은 「화면 정의 JSON → UXML + USS」** 가 자연스럽다. AI 는 JSON 만 뱉고 코드가 UXML 을 짓는 구조가 그림·소리 툴 공통 결정(「AI 는 짧은 JSON 만 뱉는다」)과 그대로 맞는다.
- **안전장치** : UI Toolkit 을 못 쓰는 프로젝트를 위해 같은 JSON 에서 uGUI 프리팹을 굽는 길을 열어 둘 수 있다. 다만 **1차에서는 하나만 한다** (둘 다 하면 검수가 두 배).

## 6. 기반 에셋 후보

**결론** : **Kenney 한 곳이면 된다.** CC0 라 출처 표기 의무도 없고, 타일 툴이 이미 Kenney 를 기본으로 쓰기로 했다.

## 8. AI 로 만들 수 있나

**결론** : **아이콘만 AI 후보, 프레임(패널·버튼)은 코드가 낫다.** 「그림은 가능하면 코드로」 원칙에 정확히 맞는다.

| 대상 | AI | 코드 | 판정 |
| --- | --- | --- | --- |
| 아이콘 (아이템·스킬) | 종류가 많고 모양이 제각각이라 코드로 못 만든다 | ❌ | **AI 또는 손그림.** PixelLab 이 후보 |
| 패널·버튼·바 프레임 | 매번 다른 걸 뱉어 그림체가 흔들린다 | ✅ 테두리 색·모서리 반지름·그림자 폭 몇 개면 그려진다 | **코드.** 결정적이고 팔레트도 지킨다 |
| 상태 변형 (눌림·비활성) | 필요 없다 | ✅ 명도 이동 · 1px 내림 · 회색화 | **코드.** 규칙이 단순하다 |
| 색 변형 | 필요 없다 | ✅ 팔레트 램프 스왑 | **코드.** 스프라이트 툴 것 그대로 |

- **PixelLab 에 UI 생성 도구가 있다.** 「Create UI Elements」로 체력바·버튼·인벤토리 칸·아이콘을 한 장씩 만들고, **최소 캔버스 16×16** 이다. 상업 이용 가능. 기존 결정(「PixelLab 은 선택 제공자, 대량 생성용이 아님」)과 그대로 맞다.
- **프레임을 코드로 그리면 덤이 크다** : border 값을 뽑을 필요가 없다. **그릴 때 이미 아는 값**이라 그냥 같이 적어 준다. 자동 판별 오판 문제가 통째로 사라진다.
- 그래서 **1차 목표는 「프레임 생성기 + border 동봉」**, 아이콘은 밖에서 들어오는 것으로 본다.

출처 : [PixelLab Create UI Elements 문서](https://www.pixellab.ai/docs/tools/create-ui-elements) · [PixelLab API](https://www.pixellab.ai/pixellab-api)

## 확인 못 한 것

- **Unity 에서 아무것도 안 돌려 봤다.** 이 문서의 Unity 관련 내용은 전부 공식 문서·토론글 읽기다.
- **`Auto9Slicer` 의 픽셀아트 실제 정확도** — 안 돌려 봤다. 「오판이 잦을 것」은 추측이다.
- **네오둥근모의 LICENSE 원문** — README·2차 자료는 OFL 1.1 이라 하는데 GitHub 자동판정은 `NOASSERTION` 이다. **쓰기 전에 원문을 직접 봐야 한다.**
- **UI Toolkit 픽셀아트 함정의 현재 Unity 6 버전 상태** — 흐림 이슈가 고쳐졌는지 확인 못 했다.
- **기준 해상도 값** — 320×180 등은 널리 쓰이는 값이라 적었지만 우리 게임에 맞는지는 안 정했다.
- **UI 원본 캔버스 크기** — 16/24/32 는 관례 정리이고, 우리 그림체(LPC 계열)에 맞는지는 그림체 결정 뒤에 봐야 한다.
- 신뢰도 낮은 자료 : 「광원은 좌상단」, 「모서리 3~4px」 같은 관례는 블로그·가이드 글 근거라 규칙이 아니다.

## 설계에서 정해야 할 것

1. **UI 프로필 항목** — 기준 해상도, PPU, 아이콘 크기 가족, 프레임 원본 크기, 팔레트, 폰트와 글자 크기.
2. **border 를 그림에 적는 방식** — `.9.png` 안내선 / 별도 JSON / 파일 이름 규약 중 하나. (자동 판별은 보조로만)
3. **UI Toolkit 하나로 갈지, uGUI 길도 열지.** 1차 범위를 정한다.
4. **화면 정의 JSON 스키마** — 무엇을 표현할 수 있게 할지 (칸 나누기, 붙임 방향, 여백, 상태).
5. **캔버스 배치 방식** — `Screen Space - Overlay` + 코드 계산 배율 / `Screen Space - Camera` + Upscale RT. 글자 또렷함과 월드 격자 일치 중 무엇을 택할지.
6. **폰트 굽기를 툴이 할지 프로젝트가 할지** — TMP 폰트 에셋 생성은 Unity 에디터 안에서만 된다. 툴(CLI)이 직접 굽지 못하므로 **Unity 쪽 에디터 스크립트를 같이 넣어야 한다.**
7. **글자 서브셋 뽑기를 넣을지** — 넣으면 대사 텍스트 형식을 정해야 한다.
8. **프레임 코드 생성기의 파라미터 목록** — 모서리 반지름, 테두리 두께, 안쪽 그림자, 하이라이트.
9. **UI 검수 항목 목록** — 최소 크기 계산, 팔레트 밖 색, 짝수 크기, 여백, 상태 변형 대응 여부.
10. **UI 툴을 그림 툴의 프로필로 둘지 서브명령으로 둘지** — 9절 표를 보면 프로필 쪽이 자연스럽다.
