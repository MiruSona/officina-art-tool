# 그림·사운드 툴 결정사항

할일 문서 `Docs/Todo/AI게임스튜디오.md` 의 **3번(2D 그림 툴)** 과 **4번(SFX·BGM 툴)** 에 대해
2026-08-20 까지 정해진 것과 아직 안 정해진 것을 모은 문서다. 설계의 입력값으로 쓴다.

조사 근거는 `Docs/Research/` 의 문서들에 있다.

## 큰 원칙

1. **AI 는 짧은 JSON 만 뱉고, 실제 결과물은 코드가 만든다.**
2. **가장 큰 목적은 클라우드 AI(Claude) 토큰 절약**이다. 툴은 CLI + JSON 입력 형태로 만든다.
3. 무거운 반복 작업은 미니PC 에서 돌린다.

### 코스튬 40종을 불리는 방식

**색과 실루엣을 둘 다 쓴다.** 둘 중 하나를 고르는 게 아니다.

| 등급 | 만드는 법 | 비용 |
| --- | --- | --- |
| 실루엣이 다른 코스튬 M 종 | **LPC 기성품에서 고른다** | 손그림 0장 |
| 각 실루엣의 색 변형 K 가지 | 팔레트 스왑 — 런타임 LUT 셰이더 | 공짜 |
| 강체 부착물 (모자·왕관·날개) | 아이템당 1장 + 앵커 | 쌈 |

**결정: M 8종 × K 5색 = 40종, 손그림 0장.**

손으로 그리는 건 어떤 M 값에서도 불가능하다는 게 실측으로 나왔다.
LPC 유니버설 시트 실측 결과 **옷 1벌당 154장**(37프레임 × 4방향 + hurt 6)이라
M=5 만 해도 770장, M=10 이면 1,540장이다. 그래서 M 은 LPC 기성품에서 가져온다.

- 쓸 수 있는 LPC 조각(OGA-BY 허용 시): torso 80종, legs 19종, feet 14종, headwear 128종
- K 도 만들 필요 없다. `palette_definitions/` 에 옷 램프 24색, 통합 75색이 이미 있다

**슬라임은 따로 간다.** 몸 색 8 × 부착물 5 = 40종, 손그림 20장.

### 툴의 정체

그림을 그려 주는 툴이 **아니다.** 그림은 PixelLab 이나 사람이 그린다.

> 그림에서 앵커를 뽑아 Unity 가 바로 쓸 수 있는 데이터로 굽는 툴

하는 일은 **규격 맞추기 → 앵커 뽑기 → 검수 → Unity 데이터 굽기** 다.

```
그림 (마커 픽셀 or Aseprite slice or PixelLab estimate-skeleton)
   ↓  툴이 읽어서 뽑음
앵커 JSON  { "frame": 12, "hand_r": { "pos": [22,31], "order": "front" } }
   ↓  툴이 변환
Unity AnimationClip 또는 ScriptableObject
```

### 프로필 예시

```json
{
  "profile": "topdown_4dir",
  "directions": ["down", "left", "right", "up"],
  "frame": [64, 64],
  "baseline": 56,
  "rigs": {
    "human": ["head", "hand_l", "hand_r", "back"],
    "slime": ["top", "center"]
  }
}
```

## 정해진 것 — 사운드 툴

| 항목 | 결정 | 비고 |
| --- | --- | --- |
| SFX 엔진 | **rfxgen** (zlib) | pyfxr 에서 바꿈 |
| BGM 엔진 | mido → FluidSynth → GeneralUser GS | 전부 명령줄로 이어진다 |
| SFX·BGM 통합 | **안 함. 따로 간다** | Unity 에서도 따로 다룬다 |
| 악보 문법 | abc notation 안 씀 | 사람이 악보를 쓸 일이 없다 |

`.rfx` 는 **104바이트 고정 바이너리**(헤더 8 + WaveParams 96 = int 2개 + float 22개)로 포맷 분석이 끝났다.
Python `struct.pack` 으로 만들고 `rfxgen --input a.rfx --output a.wav` 로 굽는다. 2016년 이후 포맷이 안 바뀌었다.

**이 PC 는 Python 3.14 다.** pyfxr 은 wheel 이 3.13 까지만 있어 실제로 못 쓴다. rfxgen 으로 바꾼 판단이 맞았다.

## 정해진 것 — 로컬 LLM

**새로 추가할 모델은 0개다.**

| 역할 | 답 |
| --- | --- |
| JSON 파라미터 만들기 | 이미 쓸 Qwen + llama.cpp GBNF 로 스키마 강제 |
| 그림 검수 | **코드로 한다** (numpy/Pillow). VLM 은 안 씀 |
| 소리 검수 | 코드로 한다 (librosa + FFT) |
| 에셋 고르기 | JSON 태그 검색 |

VLM 으로 픽셀아트를 검수하는 건 근거를 갖고 접었다. 시각 회귀 테스트 정확도가 최고 45.2%,
미묘하게 다른 이미지 구분은 17.05% 다. 64×64 는 Qwen 계열에서 토큰 4개짜리이고 입력이 자동으로 늘어난다.
반면 레이어 어긋남·팔레트 튐·프레임 밀림은 numpy 로 100% 정확히 계산되고 토큰도 0이다.

**1단계는 코드 검수만 한다. 코드가 못 잡는 게 쌓이면 그때 VLM 을 붙인다.**

## 아직 안 정해진 것

1. **그림체를 어떻게 할지 — 나중에 정한다.**
   사람 캐릭터를 어떻게 그릴지 아직 안 정했다. 선택지는 셋이다.
   - LPC 그림체로 통일하고 슬라임을 LPC 톤에 맞춘다 (손그림 0장)
   - 슬라임 그림체로 통일하고 사람 옷을 직접 만든다 (손그림 1,232장 — 현실성 낮음)
   - 사람은 LPC, 슬라임은 별개 톤으로 두고 **의도된 차이**로 만든다

   **툴 설계는 이 답을 안 기다려도 된다.** 툴은 규격·앵커·검수·굽기를 하지 그림을 그리지 않는다.
   그림체는 "어느 소스를 쓸까" 만 정하므로, LPC 층 방식을 rig 프로필 중 하나로만 두면
   나중에 어느 쪽으로 가도 툴은 그대로 쓴다.
2. **방향 수** — 탑다운 4방향인가, 참고 이미지처럼 3방향(Front/Left/Back)인가.

## 그림체 결정 없이 지금 할 수 있는 것

- 슬라임 rig 의 앵커 뽑기 — `Docs/Example/` 에 참고 그림이 이미 있고 규격도 측정됐다
- 규격 검사(baseline, 중심, 프레임 크기), 팔레트 램프 스냅, 색 수 검사
- 팔레트 스왑 LUT 셰이더와 Unity 데이터 굽기
- **사운드 툴 전체** — 그림과 아무 상관이 없다

## 실측이 필요한 것 (지금은 못 하는 것)

- `estimate-skeleton` 의 64×64 실제 정확도와 프레임 간 떨림
- 슬라임처럼 팔다리 없는 캐릭터에 `estimate-skeleton` 이 되는지
- `.rfx` 엔디안 실물 확인 (파일 하나 만들어 보면 끝난다)
- 미니PC 도착 후: Vulkan 백엔드에서 이미지 처리 모듈이 도는지

## 설치가 필요한 것

- **Pillow** (아직 없음) — 그림 합성·검수에 필요. 설치 전에 승인받는다
- **Aseprite** — 스팀판 보유. 이 PC 에 설치 필요
