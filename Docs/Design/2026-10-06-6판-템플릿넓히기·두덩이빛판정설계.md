## 2. T1 — 목록 밖 크기 받기

### 2-1. 템플릿 JSON 꼴

```json
{
  "sizes": [[64, 64], [96, 96]],
  "size_range": [[16, 16], [512, 512]]
}
```

- `size_range` = `[[최소 W, 최소 H], [최대 W, 최대 H]]`. 없으면 지금처럼 목록만 받는다(옛 템플릿 그대로).
- `size_range` 는 **맨 위에 하나만** 둔다. 프리셋 안의 `sizes`(예 `ui9_panel` 프리셋별 크기)는 손대지 않는다. 받는 목록(`_pick_size` 의 `allowed`)은 지금처럼 맨 위 `sizes` + 프로필 크기다.
- 불러올 때 검사 : 두 쌍 모두 1 ~ `MAX_SIDE` 정수, 최소 ≤ 최대. 틀리면 `TemplateError`(종료 1, 템플릿 파일 잘못).
- 켤 템플릿 : `background` 계열(`bg_screen` · `screen_piece`) · `ui9_panel` · `prop` 계열(`building` · `machine` · 새 `prop_small`) · `character` 계열(`char_small` · `char_parts` · `cycle_char`) · 새 `char_blob`. `palette` · `motion` 은 크기 뜻이 달라 켜지 않는다. **구현된 범위** : `ui9_panel` 8~256 · `building` · `machine` 16~512 · `prop_small` 16~96 · `char_blob` 16~128 · `bg_screen` 180×180~540×1200 · `screen_piece` 540×60~540×720(너비 540 고정) · `char_small` 8~240. `char_parts` · `cycle_char` 는 범위를 켜지 않고 `sizes` 목록에 120×240 을 더했다(4장).

### 2-2. 처리 순서 (`template/run.py::_pick_size`)

1. `--size` 없음 → 지금 그대로(프로필 크기 → 목록 첫째).
2. 목록(템플릿 `sizes` + 프로필 크기)에 있음 → 지금 그대로.
3. 목록에 없고 `size_range` 도 없음 → 지금 그대로 `UsageError`(종료 2).
4. 목록에 없고 범위 밖 → `UsageError`(종료 2). 안내에 범위를 같이 적는다 : `… 받는 것 : 64x64, 96x96 · 또는 16x16 ~ 512x512 사이`.
5. 목록에 없고 범위 안 → `handler.check_values(values, size, tpl, where)` 를 **그 크기로 한 번** 부른다(프리셋이 있으면 고른 프리셋 값으로).
   - 통과 → 그 크기로 렌더. 경고 `template.size_free` 하나.
   - 실패(`TemplateError`) → **`UsageError`(종료 2)로 바꿔** 낸다. 템플릿 파일이 아니라 사람이 준 크기가 문제라서. 글은 처리기의 `_fail` 안내 앞에 `이 크기에서는 안 맞는다 : 120x40 —` 를 붙인다.

**구현에서 다듬어진 규칙 (리뷰 뒤, 2026-10-07)** :

- 맨 위 `size_range` 는 프리셋이 자기 `sizes` 를 가져도 듣는다. **프리셋 목록(없으면 맨 위 목록) 밖 · 범위 안**은 경고 `template.size_free` 와 함께 종료 0 이다. 예 : `ui9_panel --preset button --size 16x16`.
- **범위 안이어도 값이 그 크기에 안 맞으면 거절**(종료 2, 까닭이 붙는다). 예 : `ui9_panel --preset bubble --size 32x32` 는 테두리가 안 들어가 거절. 범위 숫자만으로는 「그릴 수 있다」 를 못 보장해서다.
- `size_range` 없는 템플릿(`fx_dust` · `fx_sparkle`)은 프리셋 목록 밖 크기를 종료 2 로 거절한다 : `이 프리셋은 8x8, 12x12 만 받는다 : small`.

`_pick_size` 는 크기만 돌려주고, 5번의 값 검사는 프리셋을 고른 뒤 값을 확정하는 자리(렌더 흐름 안)에서 한다 — 프리셋보다 앞에서는 값을 모른다.

### 2-3. 경고 `template.size_free`

```
template.size_free : 176x123 은 목록 밖 크기다. 가장 가까운 목록 크기 : 128x96 (숫자 값은 열쇠 "96" 으로 풀렸다)
```

- 「가장 가까운 크기」 = 목록 중 `|ΔW| + |ΔH|` 가 가장 작은 것, 같으면 목록 앞쪽.
- 값이 어느 열쇠로 풀렸는지 같이 적는다. 큰 크기에서 64 열쇠로 풀려 눈이 작아지는 일(T3)을 사람이 바로 알아보게.
- 종료 코드는 0(경고뿐).

### 2-4. 렌더 결과

- `template.json` 의 `size` 칸에 고른 크기를 적는다 — 꼴 그대로라 `check --template` 의 `template.size` 대조(`check.py::_template_compare`)가 그대로 돈다.
- `template list` · `show` 는 `size_range` 가 있으면 한 줄 더 보인다(`크기 : 64x64, 96x96 · 범위 16x16 ~ 512x512`).

## 3. T2 — 덩어리 체형 `blob`

### 3-1. 왜 새 처리기인가

`Character.compute` 는 늘 머리 상자 · 몸통 · 다리 셋으로 자른다. 값을 0 으로 줘서 끄는 길은 `Parts` · `Cycle` 까지 물려받은 셈을 다 건드린다. 몸 하나짜리는 **따로 떼는 편이 작다.**

### 3-2. 템플릿 JSON (`templates/char_blob.json`)

```json
{
  "version": 1, "name": "char_blob", "kind": "blob", "title": "덩어리 몸 (슬라임 · 둥근 동물)",
  "sizes": [[32, 32], [48, 48], [64, 64], [96, 96]],
  "size_range": [[16, 16], [128, 128]],
  "values": {
    "body_w_ratio": 0.66, "body_h_ratio": 0.55, "foot_ratio": 0.205, "widest_ratio": 0.63,
    "face_w_ratio": 0.38, "face_h_ratio": 0.23, "face_y_ratio": 0.37,
    "eye": {"16": 1}, "eye_gap_ratio": 0.36, "mouth_ratio": 0.48,
    "deco_ratio": 0.33, "deco_rise_ratio": 0.12, "deco_dx_ratio": 0.07,
    "frames": [[1, 1], [1.12, 0.83], [0.9, 1.14], [0.95, 1.06]], "frame_ms": 120
  },
  "layers": [
    { "name": "body", "kind": "body" },
    { "name": "face", "kind": "face" },
    { "name": "deco", "kind": "deco", "optional": true }
  ]
}
```

값 열쇠(`value_keys`, **구현에서 정해진 이름**) — 몸 너비 · 높이 몫(`body_w_ratio` · `body_h_ratio`), 바닥 여백(`foot_ratio`, 설계 때 이름 `baseline_pad`), 가장 넓은 줄 자리(`widest_ratio`), 얼굴 칸(`face_w_ratio` · `face_h_ratio` · `face_y_ratio`), 눈(`eye` · `eye_gap_ratio`), 입(`mouth_ratio`), 머리 장식(`deco_ratio` · `deco_rise_ratio` · `deco_dx_ratio`), 통통 튀기(`frames` · `frame_ms`). 나머지 공통 칸(`prompt` · `steps` · `sources` · `layers`)은 다른 템플릿과 같다. 숫자는 64×64 덩어리 실물을 재서 정했다(몸 42×35 · 가장 넓은 줄이 몸 높이의 0.63 지점).

- **눈 기본은 1px** : 얼굴 칸 16 에 눈 사이 15 를 맞추면 3px 눈이 칸 밖으로 나간다. 그래서 `eye` 는 `{"16": 1}` 로 두고 크기별로 키운다.
- **`frames`** : 프레임마다 (가로 몫, 세로 몫) 쌍. 넓이 몫(가로×세로)은 0.8 ~ 1.25 로 묶어 살이 붙어 보이지 않게 한다. 바닥 줄은 고정.

### 3-3. 셈과 그림

- `compute` : 몸 bbox(바닥 줄에 붙여 가운데 정렬) · 얼굴 칸 · 바닥 줄(`baseline_y`) · 눈 자리.
- **윤곽은 새 셈이다** (설계 때는 타원이었다) : 가장 넓은 줄(몸 높이의 `widest_ratio`) 위는 반타원, 아래는 바닥이 평평한 지수 4 초타원. 그래서 둥글면서 바닥이 납작하다.
- `masks` : `body` · `face` · `deco`(없어도 되는 겹). 겹 이름은 `layers` 와 같게 — 기존 처리기와 같은 약속.
- 그리기는 `draw/shapes.py` 의 도형을 쓴다.
- `check_values` : `frames` 개수 · 몫 범위 · 넓이 몫, 몸 상자가 캔버스 안(3px 이상), 얼굴 칸이 몸 상자 안, 눈 두 개가 얼굴 칸 안, 입이 몸 너비 안, 머리 장식이 캔버스 안. 틀리면 `_fail`.
- `kinds.HANDLERS` 와 `schema` 의 `KINDS` 에 `blob` 을 더한다.

## 4. T3 — 큰 사람 겹 · 걷기

- `Parts` · `Cycle` 은 크기 상한을 코드에 두지 않는다(상한은 `sizes` 데이터뿐). 그래서 **데이터 일**이다.
- `char_parts.json` · `cycle_char.json` : `sizes` 에 `[120, 240]` 을 더하고, 크기별 값 표를 **`{"8": 옛값, "120": 새값}` 꼴**로 만들었다(옛 크기는 옛 열쇠로 그대로 풀린다).
  - 열쇠를 안 더하면 `pick` 이 짧은 변(120) 이하 열쇠 중 가장 큰 것으로 풀려 눈 같은 값이 너무 작다.
  - `char_small` 은 `size_range` 8~240 도 켰다. 120×240 열쇠를 같이 더했다.
- **실측한 것** : 키 214(위 여백 26) · 머리 : 몸통 : 다리 ≈ 0.40 : 0.23 : 0.37 · 눈 13×8 · 눈 줄.
- **실물로 못 잰 어림값** : 무릎 자리(`knee_ratio`) · 눈 사이(`eye_gap`) · 걷기 오르내림. 「어림」 표시는 **`char_small` 의 note 에만** 넣었다. 다른 둘(`char_parts` · `cycle_char`)에 넣으면 목록 크기 출력이 바뀐다.
- 걷기 프레임(walk 8 · walk6 · walk12)은 바닥 줄을 고정한다.
- **눈 치수가 캔버스보다 크면 템플릿 오류로 거절**한다.
- `template render char_parts --size 120x240` · `cycle_char` 를 돌려 통과를 확인하는 시험은 `tests/test_template_tall.py` 에 있다.

## 5. T4 — 9-slice · 작은 소품 · 소용돌이

### 5-1. 9-slice 56×54

`ui9_panel` 에 `size_range` 8~256 만 켠다(56×54 가 이 범위로 들어온다). `Ui9.check_values` 가 이미 「테두리가 들어가는지」 를 보니, 너무 작으면 2-2 의 5번 길로 종료 2 가 난다.

### 5-2. 작은 소품 틀

- `building` · `machine` 은 몫 기반 `prop` 이라 T1 만으로 176×123 을 받는다.
- 새 JSON `prop_small.json`(kind `prop`) 하나 : 목록 24 · 32 · 48 · 64, `size_range` 16~96. 코드 변경 없음.
- `building` · `machine` 범위는 16~512.

### 5-3. `spiral` 모양 + `fx_swirl`

- `kinds.py` 의 `SHAPE_KEYS` 에 `spiral` 을 더한다. 받는 값 : `turns`(감는 수, 0.5 ~ 4) · `r0` · `r1`(안 · 바깥 반지름 몫) · `width`(줄 굵기 칸) · `dir`(`cw` · `ccw`) · **`phase`**(회전 몫, 0 이상 1 미만 — 설계에 없던 칸) · `dx` · `dy`(중심 옮김). 조건 : 0 ≤ r0 < r1 ≤ 1 · `width` 1~32 정수.
- 그리기 : 아르키메데스 나선 r = r0 + (r1 − r0)·t 를 각도로 촘촘히 찍고 칸에 반올림해 굵기만큼 칠한다. 프레임마다 `phase` 를 올려 돌린다(기존 `effect` 프레임 흐름 그대로). `cw` 와 `ccw` 는 정확한 거울상이 아니다(반올림).
- **검사 자리** : `kinds.py::_validate_spiral` 이 값을 검사하고, `Effect.check_values` 가 프레임의 `spiral` 도형마다 이것을 부른다.
- **효과 템플릿 프레임 상한 64** (`EFFECT_MAX_FRAMES`) — 넘으면 `_fail`.
- 새 JSON `fx_swirl.json` : 64×64 · 8프레임, `phase` 를 0.125 씩 올린다.

## 6. L — 두 덩이 그림의 빛 판정

### 6-1. 어디 일인가

`check` 가 아니라 **`style extract`** 다. `style/light.py::estimate_light` 를 부르는 곳은 `style/extract.py:336` 하나뿐. `check` 는 프로필 `style.light` 를 외곽선 판정에만 쓰므로 영향이 없다.

### 6-2. 왜 흐려지나

지금은 칸마다 「밝기 − 그 램프 덩어리 평균 밝기」 를 무게로, 「칸 자리 − 그 램프 덩어리 무게중심」 을 거리로 쓴다. 같은 램프를 쓰는 **두 덩이가 무게중심 하나를 나눠 가지면**, 무게중심이 두 덩이 사이 빈 곳에 놓인다. 그러면 각 덩이 안의 밝고 어두운 차이보다 「어느 덩이가 더 밝은가 × 그 덩이가 어느 쪽에 있나」 가 치우침을 좌우한다. 앞(아래) 덩이가 더 밝으면 위 왼쪽 빛이 「아래」 로 나온다.

### 6-3. 바꾸는 것

1. 자리 덩이 : **투명으로 떨어진 불투명 덩이**(외곽선 포함, 8방향 이어짐, `_piece_ids`)로 나눈다. 검정 선으로 안이 갈린 것은 한 덩이다.
   - **왜 바꿨나 (1)** : 처음 설계는 검정을 뺀 칸으로 나눴다. 그러면 선으로 갈린 한 캐릭터의 판정이 바뀐다(리뷰 실측 : 세로선 1줄에 `top_left` → `top`, 격자에 `unknown`).
   - **왜 바꿨나 (2)** : 칸마다 도는 파이썬 루프라 2048 그림에서 0.45초 → 34초였다. numpy 라벨로 바꿔 0.59초가 됐다.
2. 「뜻 있는 덩이」 = **8칸 이상이고 가장 큰 덩이의 10% 이상**(`MIN_PIECE_SHARE = 0.1`). 눈 반짝임 · 티끌은 센다. 큰 것부터 64개까지(`MAX_PIECES`). 뜻 있는 덩이가 **하나 이하**면 그림 전체(티끌 포함)로 옛 셈 그대로다 — 결과가 옛 판과 바이트까지 같다(15장 폴더에 `style extract` 를 옛 · 새로 돌려 출력 파일 4개와 stdout 이 같음을 확인).
3. 묶음 번호 = (램프 덩어리 번호, 자리 덩이 번호) 쌍. 무게 · 무게중심을 이 묶음으로 잡는다. 나머지(dx · dy · shift · 각도 판정 · `MIN_SHIFT` 0.05)는 그대로.
4. 덩이별 판정 : 뜻 있는 덩이가 둘 이상일 때만 덩이마다 같은 셈으로 판정을 따로 낸다. `unknown`(모름)을 뺀 판정끼리 다르면 `confidence: "low"`, 아니면 `"high"`. 덩이가 하나면 늘 `"high"`.
5. **못 고치는 경우** : 외곽선을 같이 쓰거나 외곽선이 서로 닿은 두 덩이는 한 덩이로 세어져 옛 셈 그대로다.

**구현에서 정해진 것 (2026-10-07, `style/light.py`)** :

- 덩이별 판정은 **큰 덩이부터 64개까지**(`MAX_PIECES`) 만 한다. 자잘한 덩이 수천 개에서 느려지지 않게 하려는 것이다.
- 덩이별 판정의 크기 기준은 **그 덩이 bbox 의 긴 변**이다(그림 전체 크기가 아님). `MIN_SHIFT` 0.05 를 덩이 크기에 맞춰 잰다.
- 뜻 있는 덩이가 하나 이하면(티끌뿐이면 포함) 덩이 나누기 없이 옛 셈으로 돌아간다.
- 시험은 `tests/test_light_pieces.py` 에 있다(처음 계획했던 `test_style_fixes.py` 가 아님).

### 6-4. 돌려주는 값 · 보고

- `estimate_light` 결과 사전에 `confidence` · `pieces`(쓴 덩이 수) 두 칸을 **더하기만** 한다. `light` 값 집합(top_left · top · top_right · bottom · unknown)은 그대로.
- `extract` 요약 `light` 에 `low` (confidence low 장 수) 한 칸을 더한다. `table` · `pick` · `total` 과 `light_table` 꼴은 그대로.
  - **구현에서** : 보고 파일의 `light` 에는 `low` 가 **0 보다 클 때만** 실린다(없으면 `table` · `pick` 뿐). 장별 `light_confidence` 는 low 일 때만, 경고 `light_mixed` 는 low 가 1장 이상일 때 실린다.
- `low` 가 1장 이상이면 경고 `light_mixed` : `빛 판정이 덩이끼리 엇갈린 그림 N장 — 표를 그대로 믿지 말고 눈으로 본다`.
- 종료 코드 변화 없음.

### 6-5. 옛 결과와 달라지는 것 — 어디에 알리나

같은 그림이라도 두 덩이 이상이면 판정이 바뀔 수 있다. 알릴 자리 셋 :

- `ArtTool/Docs/History/` 의 6판 기록에 「`style extract` 빛 판정이 덩이별로 바뀜 — 옛 프로필의 `style.light` 는 다시 뽑아 비교」 한 줄.
- `README` 의 `style extract` 절에 한 줄.
- `arttool-usage` 스킬의 화풍 뽑기 대목에 한 줄.

프로필은 사람이 붙이는 것이라(자동으로 안 붙는다) 옛 프로필이 저절로 바뀌지는 않는다.

## 11. 못 정한 것 · 사용자에게 물을 것

**사용자에게 물을 것**

1. **120×240 사람 그림 한 장**(가능하면 겹 · 걷기 프레임까지) — 머리 : 몸통 : 다리 비율과 눈 크기를 재서 "120" 열쇠를 채운다. 없으면 64 열쇠 비율을 그대로 늘려 넣고 「어림값」 으로 표시한다.
2. **42×35 둥근 몸 그림 한 장** — `char_blob` 기본 몫(몸 · 얼굴 칸 자리)을 잰다.
3. 빛 판정이 바뀌는 것을 **History · README · 스킬 세 곳 알림**으로 충분한지, 아니면 `style extract` 실행 때 한 번 안내 글을 띄울지.

**못 정한 것 (구현 때 정한다)**

- 템플릿마다 `size_range` 숫자.
- `spiral` 그리기에서 칸 반올림 뒤 끊김을 메우는 방법(선 잇기 vs 각도 더 촘촘히) — 구현 때 그려 보고 고른다.
- `confidence` 를 덩이 판정 「다름」 하나로만 볼지, 덩이 크기 차이(작은 덩이 무게 낮추기)까지 볼지 — 1차는 「다름」 만.
